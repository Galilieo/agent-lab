# agent-lab 代码注释规范

本文件约定如何给源码写说明，服务于“能看懂文件负责什么，以及代码为什么这样写”。学习进度仍以 [`agent-lab总体学习路线.md`](./agent-lab总体学习路线.md) 为准。

参考 [PEP 8 的注释规范](https://peps.python.org/pep-0008/#comments) 与 [PEP 257 的 docstring 规范](https://peps.python.org/pep-0257/)。本项目用中文解释业务，保留代码中的英文标识。

## 1. 文件开头说明职责和位置

手写 Python 文件使用模块 docstring：先用一句话概括职责，再按需说明由谁调用、依赖什么、是否有外部调用或文件写入。

- app 文件交代在 HTTP → Agent → LLM / Tool → SQLite 链路中的职责。
- tests 文件交代测试保护什么、fake 替代哪一层、哪些本地代码真实执行。
- playground 文件交代练习目标、运行命令及写文件等实际副作用。
- 不在注释中维护易过时的阶段状态、测试数量或提交历史；这些由正式路线和 Git 记录。

## 2. 函数说明调用者需要知道的契约

简单函数用一句话。复杂函数用“摘要 → 空行 → 约束或必要的 Args / Returns / Raises”结构。

Args / Returns / Raises 是本仓库选择的说明格式，不是 PEP 257 强制的标题。类型标注已经表达清楚的内容不用机械重复；重点写含义、特殊值、副作用和调用方责任。

例如现有数据库函数的说明：

```python
def create_connection(
    database_path: str = ":memory:",
) -> sqlite3.Connection:
    """创建 SQLite 连接，并为这个连接启用外键检查。

    Args:
        database_path: 数据库文件路径；默认 :memory: 只存在于当前连接。

    Returns:
        由调用方负责关闭的连接。事务是否提交也由调用方决定。
    """
```

## 3. 块注释解释原因与边界

使用 `# ` 开头，跟随所在代码的缩进。优先说明：

- 为什么模型等待必须放在数据库事务之外。
- 为什么先读旧历史再保存当前问题，防止同一问题进入模型两次。
- 为什么零行 SELECT 还需要由 Python 主动抛出业务异常。
- 为什么模型调用预算要在执行工具之前检查。
- 为什么 HTTP 200、有效 JSON、可用模型结果和整轮 Agent 成功是不同层次。

不要逐行重复 `append`、赋值或 `return` 的字面含义；注释与代码不一致时应修正注释。较长说明分行，避免横向滚动。

## 4. 测试注释说明行为和证据

测试函数的 docstring 说明场景与预期。复杂准备、刻意异常输入、消息关联和前后状态比较处再补少量块注释。

明确区分 fake 模型、真实本地工具、真实 SQLite、同进程 MCP 与 stdio 子进程；不把预设模型响应写成真实模型选择能力的证据。

已补齐的学习 TODO 应移除。RED 表示目标能力还缺失，注释只能说明预期行为，不能声称尚不存在的实现已经完成。

## 5. 不让说明意外改变接口契约

Python 的 docstring 可被框架读取。现有 FastAPI 路由、MCP 注册函数和 Pydantic 模型的说明可能参与接口文档、工具描述或 Schema 生成。

纯补注释时保留这些对象已有的 docstring，使用相邻块注释解释职责；不修改工具 description、参数声明、模型提示词、SQL 字符串或日志内容。

JSON 和生成的锁文件不强塞 Python 注释；配置文件的职责可以在 README 中解释。不要添加真实密钥、请求头或用户敏感正文作为注释示例。
