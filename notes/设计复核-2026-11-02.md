## 结论

原生 Agent、SQLite 记忆和 Chroma RAG 的总体方向可以保留。当前主要欠缺在于模型边界校验、完整轮次的状态管理、统一上下文预算，以及把实验接口转为业务接口时的身份和数据范围。问题不是缺少框架、插件系统或更多 Agent。

已用 fake HTTP、fake Agent 和临时 SQLite 复现模型响应分类、会话并发和删除期间在途提取三个问题。它们与尚在进行的引用检查、RAG 路由接线分开记录。其余结论来自源码检查或明确的设计边界，不宣称已经测出线上问题。

## 2. 需要修正：模型适配层的成功与失败边界不完整

位置：`app/services/llm.py:167`、`:175`、`:227`；`app/services/agent.py:140`；`app/main.py:521`。

目前只转换 ReadTimeout、ConnectError、HTTPStatusError，正文提取只捕获 JSONDecodeError/KeyError。数据类的类型注解不会在运行时校验返回值。

隔离复现结果：

| 上游响应/异常 | 当前实际结果 | 后续影响 |
| --- | --- | --- |
| `{"choices": []}` | IndexError | 绕过 LLMRequestError 分类和相应持久化路径 |
| `{"choices": [{"message": null}]}` | TypeError | 同上 |
| 无工具调用且 `content: null` | 返回“成功” LLMResult，answer 为 None | Agent 当作最终回答；落到非空消息字段时失败 |
| 无工具调用且 `content: 123` | 返回“成功” LLMResult，answer 为 int | 内部契约与 HTTP 字符串响应契约不一致 |
| ConnectTimeout | 原样抛出 ConnectTimeout | 不进入当前读取超时或连接失败的业务分类 |

建议先为“最终文本响应”和“工具调用响应”分别定义有效形状，允许工具调用时 content 为 None，但最终回答必须满足文本契约。将预期的 HTTPX 超时、传输异常统一转换为现有错误类型；保留必要元数据，不用宽泛捕获掩盖实现错误。

这项适合近期修正，只需少量有代表性的契约测试，无须重写为完整 SDK。修正必须连同日志/调用记录边界验证，不能只让 HTTP 看上去不报错。

## 3. 需要在业务接入前确定：同一会话的完整轮次没有执行协调

位置：`app/main.py:390`、`:420`、`:516`；`app/database.py:539`。

短事务正确解决了网络等待占用数据库的问题，但不等于整个聊天轮次已经串行或原子化。A 提交问题并等待模型时，B 能读取尚无回答的 A，再提交自己的问题和回答。历史按 created_at/message_id 排序无法恢复业务上的轮次归属。

临时 SQLite + fake Agent + asyncio.Event 确定性复现：

```text
A 开始，模型暂不返回。
B 开始，看到的 history = [user A]。
B 返回；再让 A 返回。
持久化历史 = [user A, user B, assistant B, assistant A]。
```

参考：OpenCode execution.ts 把 SessionRunCoordinator 实例绑定到 SessionSchema.ID；Harness 显式记录 turn/start、step/start、step/end 和 turn/end，而不是仅用完成时间推断轮次。

建议先决定心屿交互：同会话排队、拒绝重复运行，还是把新输入当作对当前任务的 steering。最小接入可选择排队或明确返回 busy；记录 turn/request ID 和状态，用于重试、错误显示和历史关联。若部署多进程，不能把 asyncio.Lock 宣称为跨进程保证；届时才判断是否需要共享租约。

工具请求和结果目前只留在本轮内存，model_call 主要保存调用元数据；因此可以做耗时/失败分类追踪，尚不足以重放一次工具决策链。需要排查具体工具行为时，可增加精简结构化事件，不必直接复制事件溯源框架。

## 4. 已知边界得到复现：删除记忆不能阻止旧的在途提取重新写入

位置：`app/main.py:296`、`:308`；`app/database.py:304`；`app/services/memory.py:132`。

已有实现保护了“不重扫旧历史”的顺序执行场景。但旧请求在 await 提取时，新的删除事务可以先成功；提取恢复后仍能通过来源校验，再次 upsert 同 key。来源确实属于用户，不代表它仍拥有覆盖后来删除决定的权限。

隔离复现：已有 answer_language 记录；启动新一轮提取并暂停；删除 all 范围同 key，实际 deleted_count=1；恢复旧提取；数据库重新出现 answer_language 记录。

这不是把已有顺序测试判为失败，而是验证了方案已声明的并发边界。若心屿允许删除与提取交错，应记录记忆变更版本或删除水位，在写入前核对提取基于的版本；较晚的明确重新保存可以建立新版本。单会话锁不能独自解决同用户跨会话的全局记忆竞争。

最小实验仍可保留顺序执行范围；若产品承诺“删除后立即不再出现”，此项须在该承诺上线前处理。

## 5. 设计欠缺：预算分散在消息条数和两个局部字符串中

位置：`app/main.py:400`；`app/services/llm.py:140`；`app/services/rag_context.py:17`；`app/services/memory.py:184`；`app/schemas.py:23`。

记忆限制约 1000 字符，RAG 限制约 4000 字符，历史只取最近 10 条。当前问题只有最短长度限制，工具结果和工具 schema 也没有进入统一预算。三个局部限制都通过，不代表最终模型请求能装进上下文窗口；字符数量也不等于 Token 数量。

Hermes context_engine.py 提供针对完整 messages 的选择/压缩接口，并区分持久化历史与本次请求内容；Harness 的 preStep/step 集中组装上下文。这里值得借鉴的是职责集中，而不是立即接入摘要模型。

建议增加统一的请求上下文组装职责：先预留回答额度，再计算系统指令、工具、当前问题、历史、记忆、RAG 和本轮工具结果的总预算。优先明确裁剪顺序，保护工具请求/结果配对，不将超长当前问题静默截断成另一个问题。学习阶段可先做保守估算并记录误差，不必立刻实现复杂压缩。

## 6. 产品契约欠缺：记忆辅助流程与回答正文耦合

位置：`app/main.py:278`、`:332`、`:554`；`app/services/memory.py:87`；`app/schemas.py:29`。

主回答已提交后，HTTP 仍 await 一次提取，再做持久化和反馈文本更新。当前失败隔离保护了成功/失败结果，却不隔离提取等待时间；没有本轮整体截止时间时，用户仍须等辅助调用完成。尚未实测新增延迟，不给出性能改善数字。

保存状态直接拼进 assistant 正文，界面显示、历史内容和模型生成文本被合并。提取调用也未进入现有主聊天 model_call 的持久化记录；因此现有用量统计不能直接代表整次请求的总成本。

建议保留模型不自行宣布“保存成功”的原则，逐渐将回答、memory_operation 状态、warnings、sources 分开返回。参考 Hermes persisted_turn_receipt 的做法：界面凭已提交消息 ID 对齐结果，不凭文案猜测。如果后续选择后台提取，需要同时设计任务寿命、失败反馈和删除竞态；简单 create_task 并不自动获得可靠后台任务。

同步处理本身可以继续用于当前小实验，不要求为了这一项立刻引入队列。先明确产品是否允许等待，以及如何向用户展示操作结果。

## 7. RAG 的三个边界应保留，并补足验证

位置：`app/services/vector_store.py:83`；`app/services/rag_context.py:9`；`app/services/rag_citations.py:17`；`app/main.py:423`。

### 7.1 检索返回了片段，不等于资料足够回答

当前 TopK 不做相关性阈值过滤，非空库通常仍会给域外问题返回最近片段。因此“没有片段就直接资料不足”只能覆盖空库或预算后没有可用片段，不能证明域外问题会被拒答。

不建议拍一个距离阈值作为补丁。先用少量固定问题覆盖明确可答、同词不同意图、资料未包含答案及跨片段问题，分别观察检索命中、回答正确、引用正确和不足时拒答。由结果决定是否需要阈值、混合检索或 reranker，不先堆组件。

### 7.2 引用 ID 合法，不等于片段支持结论

现有 CitationCheck 设计只返回合法来源和未知 ID，上层决定显示警告、拒答或重试，职责划分合理。白名单必须来自预算后的 RagContext.sources；提供资料与实际引用也必须区分。

Hermes 专门引用技能同样把来源登记、正文检查、错误/警告和后续处理分开；其 evidence 文本匹配也不是语义蕴含证明。当前用户选择“保留回答、明确标注无效引用、不生成来源链接”有合理性，是否改成阻断应由产品场景决定，不能仅因为另一项目更严格就覆盖该选择。

本次检查时 CitationCheck 尚未完成且正在被编辑，/chat 尚未传入 rag_context。这两项是既有待办，不能说成完成后退化的架构错误。

### 7.3 来源编号在索引更新后可能指向另一段原文

当前 source::chunk_index 很适合作为本轮白名单；但源文件编辑并重新切分后，相同编号可能对应新内容。未来把历史回答里的 ID 链接到“最新索引”会失去回答当时的证据。

建议在保存 RAG 回答时保留实际使用的片段快照或文档版本/内容哈希。当前回合内的引用检查不必因此改为复杂的全局来源服务。

## 8. 接入心屿的边界：归属一致性与可信身份需要分开

位置：`app/schemas.py:23`；`app/main.py:393`、`:93`、`:118`；`app/services/vector_store.py:12`、`:60`。

当前 user_id 来自请求体，数据库检查“请求所说的用户”和“会话登记用户”一致。这对机制实验是合理前提，但未证明调用者真的代表此用户。心屿必须由 Java 登录态/可信内部调用提供身份，Python 校验内部来源，不能直接信任公网调用方自报 user_id。

Chroma 使用单一专用笔记集合，全量 sync 会删除不属于当前目录快照的 ID，也没有每用户的检索过滤。单一公共课程库可以继续这样用；若接入私人日记或用户资料，需明确知识库/用户范围，并在检索前约束可见数据，不能在模型输出后才做过滤。

当前 sync_chunks 的 upsert/delete 没有跨步骤事务，文档也已明确。嵌入失败前不动旧索引是正确保证，但不能扩大为任意写入失败或并发更新都保持完整旧快照。若未来允许一边更新一边问答，可考虑新版本构建成功后切换，或先限制更新窗口。

这些是业务接入设计要求，不要求现在把 agent-lab 变成多租户生产平台。

## 9. 应当保留的设计

- 原生 LLM、Agent、工具/MCP、存储和纯上下文函数分层，能够观察真实执行链；框架后续用于对照。
- 模型等待放在短数据库事务之外；最终回答与主调用记录一并提交。
- 记忆失败不撤销主回答，管理存储错误不伪装成空数据，身份和来源由应用绑定。
- 记忆固定少量 key，先覆盖合并再分层选择；不因参考产品功能多就立即换成向量记忆平台。
- 文档处理与在线问题检索分开；整批嵌入成功后再开始同步索引。
- RAG 按完整渲染文本计入预算，来源对应实际装入的片段；不把资料塞进系统权限层。
- 最大模型调用预算耗尽时不再执行无法回传的工具动作。
- pytest 隔离真实模型，临时真实 SQLite/Chroma 验证持久化；组件探针、正式路由与效果评估分别记录。

## 10. 本次验证与后续优先级

实际执行 `.venv/bin/python -m pytest -q`：**93 passed、2 failed**。两个失败均在正在编辑的引用检查单元，本次运行时为 NameError；随后只读检查可见用户仍在输入该函数，所以这不是稳定提交的回归结论，也没有据此代改核心实现。

独立隔离复现：模型边界 5 个代表情形、同会话两个并发请求、删除期间恢复旧提取。均使用假模型/假 HTTP 和临时 SQLite，没有连接 Ollama、云端聊天 API 或业务数据库，没有修改持久配置。

首次使用 uv 启动复现被默认缓存目录的沙箱权限阻止，随后直接使用项目 `.venv/bin/python` 完成同一项检查；不是依赖失败，也未修改权限配置。

建议处理顺序：

1. **当前可以修正的真实缺口**：模型响应与传输错误边界；同时按现有设计完成引用检查、显式空资料兜底和 RAG 路由验收。
2. **心屿接口设计时先确定**：可信身份、会话执行顺序、请求/轮次 ID、结构化来源与操作状态，以及整体上下文预算。
3. **在相应产品能力开放前处理**：并发删除防重建、私人知识库范围、索引并发更新、历史引用快照；由实际场景决定实现深度。

本评审不改变原有 LangChain、LangGraph、SSE、优秀产品学习及心屿接入主线，不以 11 月 8 日目标自动删减既定内容。也不把全部发现强加成当前 RAG 阶段的前置任务。
