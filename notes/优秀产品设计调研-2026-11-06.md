# 优秀 Agent 产品设计调研：后续逐步带读的选题依据

核验日期：2026-11-06。用户要求先扩大研究面，之后逐步讲解多个方面，并筛选有实际设计价值的方案。本文是研究准备与判断，不代表课程已经讲完、产品已经实测或方案已经适用于心屿。

## 研究范围与时效性

本轮补读 Claude Code 的工作机制、最佳实践、会话/回退和子代理文档；Hermes 的记忆与技能文档；OpenCode 的权限、工具与客户端/服务端文档；重新核验 DeepSeek Harness 官方 README。pi 沿用此前已经固定的源码专题；本轮不把默认分支网页当成新固定源码。

证据分层：pi 专题有固定源码；其余本轮主要是当日在线官方文档的机制阅读，未固定实现 SHA、未运行产品。文档记载的行为与我的设计分析分别写明。进入某项实现带读前，再固定对应开源版本并核验调用链；闭源部分只讲官方说明与可观察行为。

OpenCode 标准文档含 OpenCode 1 的具体说明；先前读的 dev.opencode.ai/v2 是另一文档入口，本轮不将两者的配置/API拼成一个版本。DeepSeek Harness README仍标记 developer preview、可能有破坏性变更，不因知名就称为成熟稳定架构。

Anthropic 两篇工程文章分别发表于2025-09-29、2026-01-09。本轮重新打开，用作上下文与评估的原则材料，不冒充2026-11-06新发布结论，也不替代当前产品源码。

## 如何筛选“值得学的好设计”

不能仅凭项目知名、功能数量或作者评价判断。优先考虑：

1. 对应一个明确的用户问题或真实失败，能够解释机制为何有效。
2. 核心状态、执行边界和失败后的结果明确，用户能够理解并控制。
3. 复杂度与收益相称，能说清新增延迟、费用、维护成本和失效条件。
4. 可观察、可验证，能区分模型声称成功与实际完成。
5. 适用条件与心屿相关；个人开发终端的信任模型不能直接搬到多用户服务。

本文说“值得优先讲”只表示已找到有解释力的机制与取舍；相对于替代方案的效果，仍需对应场景验证。

## 已筛选的设计及其取舍

### 1. 上下文分层与按需获取：先知道去哪里找，再读取内容

官方材料：Anthropic上下文工程文章说明用路径、查询、链接等轻量引用，在运行时按需取资料；也讨论预先注入与自主检索结合的方式。Hermes技能文档给出技能目录→完整技能→具体参考文件的逐层加载。

设计判断：有价值的部分是让信息进入上下文的时机与粒度明确，适合资料多、工具多的场景。代价是多次检索带来延迟，模型也可能找错或漏读；它不天然比预先检索更好。

心屿联系：对照已有memory_context、rag_context和search_knowledge，讨论哪些信息应随请求提供，哪些由模型按需查询。验证时比较同题的资料命中、回答依据、请求次数与延迟，不只比较token。

来源：[上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)、[Hermes技能](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)。

### 2. 长期记忆、会话历史与当前输入分别管理

官方材料：Hermes将精选记忆与用户资料存入两个有容量限制的文件，在会话开始时形成固定系统提示快照；会话内工具能写入最新记忆，系统提示快照到下一会话才刷新。文档解释这样做是为了保持前缀缓存。

设计判断：分层和容量约束便于维护，也让稳定信息有明确生效时机。代价是记忆写成功与本次提示更新不是同一件事，持续很久的会话需要处理信息新鲜度。不能直接推断它比动态选择记忆更有效。

心屿联系：已有Memory V1.1方案可以作为对照；重点看改口、删除、临时要求与永久偏好的区别，以及用户能否检查/修正记忆。先不改成同款文件系统。

来源：[Hermes Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)。

### 3. 以实际结果定义完成，而不是以模型最后一句话定义完成

官方材料：Claude Code最佳实践建议给Agent可运行的检查，并区分提示词约定与程序执行的约束；Anthropic评估文章区分执行轨迹与环境中的最终结果，介绍代码、模型及人工评分的不同适用范围。

设计判断：适合优先学习，因为它直接限制“看起来完成、实际没完成”的问题。代价是检查本身可能不完整，自动测试也不能覆盖全部产品效果；模型评分还需要校准。

心屿联系：保存记忆应检查真实写入，资料回答应检查引用与来源，审核建议不能等同于业务处理成功。复用已有固定合成题和程序校验，不因学习文章就另建大型评测平台。

来源：[Claude Code最佳实践](https://code.claude.com/docs/en/best-practices)、[Agent评估](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

### 4. 权限控制与确认交互：哪些由模型决定，哪些由程序执行

官方材料：OpenCode标准权限文档定义allow/ask/deny，可按动作及工具输入匹配；Claude Code最佳实践区分给模型的指令与由harness落实的约束。

设计判断：可解释的权限规则让自动化与人工确认有明确分界。但规则越细，维护与匹配错误越复杂；确认过多也会增加用户负担。工具权限和操作系统沙箱是不同层，前者不能自动替代后者。

心屿联系：区分程序按登录身份限制资料范围、模型提出工具请求、用户同意某项业务动作。开发者终端的“本会话允许所有编辑”不宜直接当成用户资料访问规则。

来源：[OpenCode权限](https://opencode.ai/docs/permissions/)、[Claude Code最佳实践](https://code.claude.com/docs/en/best-practices)。

### 5. 用户控制与纠正：停止、排队、插话各有时机

官方材料：此前已读pi固定源码及Claude Code/Hermes当日官方文档，对比取消、steering、follow-up与重新请求模型。细节见pi专题4.3/5.1。

设计判断：好的交互需要解释当前正在生成、工具执行、等待确认还是已结束，以及用户的新输入何时生效。不会仅因后台有一个队列就自动形成好体验；需要避免用户误以为工具已被立即停止。

心屿联系：前端状态与后端事件应对应；“停止显示”“取消生成”“终止工具”和“退出页面”分别设计。先利用已学SSE概念解释，不自动扩成完整工具流式迁移。

来源：[专题1](./pi专题/tutorial.md)、[Claude Code机制](https://code.claude.com/docs/en/how-claude-code-works)、[Hermes CLI](https://hermes-agent.nousresearch.com/docs/user-guide/cli)。

### 6. 可恢复与可撤销：对话、代码和外部动作分别处理

官方材料：Claude Code回退文档允许分别恢复代码、对话或两者；代码恢复依赖有记录的文件快照，文档同时说明覆盖限制。会话恢复与回退是不同操作。

设计判断：有价值的是明确“撤销什么”，支持尝试替代方案，并提供恢复范围。代价是多份状态可能不再一致，用户需知道保留了什么；这种回退不能当成任意业务动作的通用事务。

心屿联系：会话分支、重新回答、删除记忆、撤销业务动作不可共用含糊的“恢复”语义。先讨论用户预期，再决定是否需要相应实现。

来源：[Claude Code Checkpointing](https://code.claude.com/docs/en/checkpointing)、[会话管理](https://code.claude.com/docs/en/sessions)。

### 7. 技能、工具与插件分工：复用流程知识，同时控制扩展复杂度

官方材料：Hermes技能按需加载知识；OpenCode工具文档区分内建工具、自定义工具与MCP接入。DeepSeek Harness README以插件架构为核心定位，但本轮只重新核验README，未深读当前插件生命周期。

设计判断：技能适合复用指导与流程，工具适合执行具体动作，插件适合接入产品生命周期；把三者分清比增加插件数量更重要。技能可能过时，工具有副作用，插件增加初始化、依赖与兼容负担。

心屿联系：整理稳定业务能力与可变提示策略的边界；不预设要增加全套插件系统。Harness保留为后续源码选题，不能依据口号就判定其方案最佳。

来源：[Hermes技能](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)、[OpenCode工具](https://opencode.ai/docs/tools/)、[Harness官方仓库](https://github.com/deepseek-ai/deepseek-harness)。

### 8. 多代理：按信息边界拆任务，而不是按角色名堆Agent

官方材料：Claude Code子代理文档说明独立上下文、工具与权限配置，以及把大量检索/日志留在子上下文，只带回摘要；也明确额外请求消耗与上下文交接差异。

设计判断：值得研究的是上下文隔离与职责边界。独立且信息量大的子任务可能适合；需要共享细节、频繁同步的任务未必适合，摘要还可能丢失证据。没有可测收益时不优先引入。

心屿联系：将来按实际需求比较独立审核/检索辅助与单Agent调用工具；本轮未创建或执行子Agent，也不把“多Agent”列为必需架构。

来源：[Claude Code子代理](https://code.claude.com/docs/en/sub-agents)。

### 9. 客户端与执行服务分离：界面变化不直接决定任务生命周期

官方材料：OpenCode标准服务端文档说明TUI是客户端，HTTP服务提供API及事件接口，并支持其他客户端接入。

设计判断：执行生命周期与显示层分开，有利于复用执行服务；但需要额外处理鉴权、会话归属、断连状态与事件同步。仅有HTTP接口不能证明断网重连或任务可靠性。

心屿联系：可对照Java业务后端、Python AI服务和前端的分工，明确谁持有任务状态、谁取消任务、谁负责保存最终结果。不照搬本地开发工具的信任与部署假设。

来源：[OpenCode Server](https://opencode.ai/docs/server/)。

## 后续带读安排

这些是有依据的选题池，不是一次新增九个开发任务，也不作为lab交接前的九门必修课。

优先从“上下文怎样选、何时取资料”进入，再串联长期记忆与结果验证。后续穿插权限/确认、交互/恢复、服务边界与扩展机制；多代理在任务确实适合时再深入。主读按问题轮换，不固定pi，也不为凑产品数量机械重复同一概念。

每次以一个具体用户场景展开：产品行为与职责→关键数据/事件链→设计理由与替代方案→代价/失败边界→与lab或心屿的关系。需要源码的课先固定版本；没有真实体验时明确是文档或静态源码阅读。适合的小实验再做，不要求读到一个功能就实现一个功能。

当前进度：研究准备已整理；用户已确认continue答疑的主干理解，未据此宣称整个执行/恢复专题已掌握。后续逐步带读，当前没有新产品实测、核心改动、pytest或真实模型请求。
