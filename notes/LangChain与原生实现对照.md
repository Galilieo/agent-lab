# LangChain 与原生实现对照

本专题记录当前源码中的职责与已核验差异。学习进度以[总体路线第14节](./agent-lab总体学习路线.md#14-当前下一步)为准。

## 先分清三个入口

| 组合 | 循环由谁管理 | 单次模型调用 | 返回什么 |
| --- | --- | --- | --- |
| 正式原生链路 | `agent.run_agent` | `llm.generate_reply` | 项目 `AgentResult` 或项目异常 |
| 本轮契约对照组合 | 同一个 `agent.run_agent` | `langchain_adapter.generate_langchain_result` | 相同项目结果/异常契约；仅在测试或显式探针中替换入口 |
| 预建框架 Agent | `create_agent` 构建的框架流程 | `ChatDeepSeek` | 当前包装函数返回完整消息列表，框架异常继续传播 |

正式 `/chat` 继续使用原生链路。本轮共享验收比较前两种组合；不能把结果写成预建框架 Agent 已完成业务迁移。

阅读位置：[原生模型入口](../app/services/llm.py)、[框架适配](../app/services/langchain_adapter.py)、[原生循环](../app/services/agent.py)、[预建 Agent](../app/services/langchain_agent.py)。

## 框架封装了什么，应用仍负责什么

| 环节 | 原生实现 | 框架实现与应用边界 |
| --- | --- | --- |
| 输入消息 | 应用组装协议字典列表 | 模板和消息占位形成消息对象，由 SDK 序列化；参考顺序仍由应用指定 |
| HTTP 与响应 | HTTPX 请求，应用解析协议字段 | ChatDeepSeek 和底层 SDK 处理请求/响应协议，返回 `AIMessage` |
| 工具声明 | 请求体中传 `tools` | `bind_tools` 绑定声明；这一操作不执行工具 |
| 参数处理 | `LLMToolCall.arguments` 保留原字符串 | 框架把可解析参数放进 `tool_calls`，不可解析项放进 `invalid_tool_calls`；本项目从 HTTP 观察保留原始请求再映射 |
| 工具执行 | 原生 Agent 调 `execute_tool` 等执行入口 | 本轮对照仍由原生 Agent 执行；预建框架 Agent 则通过 StructuredTool 等组件接线 |
| 业务结果与错误 | `LLMResult` 和自定义异常 | 适配层将框架结果/SDK 异常转换成同一项目契约 |
| 数据与权限 | 路由处理会话归属、事务和持久化 | 框架不会自动接管已有 SQLite、HTTP 状态映射或权限规则 |

当前安装版本的消息转换源码没有在 `AIMessage.additional_kwargs` 中保留原始 `tool_calls`。该结论来自本机版本核验，不应泛化为所有版本。

## 一个计算请求的数据流

```text
run_agent 接收问题、history 和参考文本
→ 本轮 tools 与 additional_messages 交给选定的模型入口
→ 得到 LLMResult，先加入 model_calls
→ 若有工具请求，校验并执行真实计算器
→ assistant 工具请求 + 对应 tool_call_id 的结果进入 additional_messages
→ 第二次模型调用返回最终文本
→ AgentResult 携带最终回答与两条调用记录
```

第二次模型超时时，`AgentRunError` 携带此前成功调用及 `LLMTimeoutError` 原因。参数字符串非法时，工具层抛出 `JSONDecodeError`，Agent 包装成 `AgentToolError` 并保留已经成功的模型调用。工具处理错误不虚构额外失败模型调用。

## 共享场景怎样验收

[test_model_backend_contract.py](../tests/test_model_backend_contract.py) 使用一份参数化测试：两个模型入口分别运行三个相同场景，共六例。

| 场景 | 实际模型请求数 | 保留的成功调用数 | 项目结果 |
| --- | --- | --- | --- |
| 请求计算后给出回答 | 2 | 2 | `AgentResult`，最终回答为预设文本 |
| 请求计算后第二次超时 | 2 | 1 | `AgentRunError`，原因是 `LLMTimeoutError` |
| 工具参数为非法 JSON 字符串 | 1 | 1 | `AgentToolError`，原因是 `JSONDecodeError` |

测试使用同样的历史、Memory/RAG 参考文本和模型响应，通过 MockTransport 隔离外部 HTTP。实际执行原生 Agent 循环、两种模型入口、框架 SDK 和计算器。检查返回字段、原始参数空白、消息顺序、工具结果 ID、Token、错误归属和输入不被修改。

`backend_run` fixture 的 `params` 选择模型入口，测试的 `scenario` 参数选择情景。`pending` 仅在实际 HTTP 请求到来时消费下一份响应。`SimpleNamespace` 为原生模块提供局部 HTTPX 替身，避免把 SDK 使用的全局客户端类改成工厂函数。

本轮验证既有实现，不新增业务行为，不为验收制造 RED。2026-11-04 目标实际为 **6 passed**；全量证据在正式路线记录。预设 HTTP 响应不能证明真实模型选工具的能力、回答质量、检索质量或部署效果。

## 真实模型验收补充

用户要求使用 `.env` 配置进一步验证。通过显式命令加载进程环境，运行[真实验收脚本](../playground/langchain_live_acceptance.py)，结果保存在[本次报告](../playground/results/langchain_live_acceptance_2026-11-04.json)。不读取或打印配置文件内容和密钥。

原生入口和框架适配入口各运行四类问题，再单独运行预建Agent计算器，共九组场景：

| 场景 | 原生入口 | 框架适配入口 | 独立预建Agent |
| --- | --- | --- | --- |
| 历史中的临时代号 | 正确复述青榆7314 | 正确复述青榆7314 | 未运行此题 |
| 工具计算23乘19 | 实际调用计算器，返回437 | 实际调用计算器，返回437 | 实际调用计算器，返回437 |
| 合成资料中的两个事实 | 标签及恢复顺序正确，引用分别对应service/recovery | 事实与引用均正确 | 未运行此题 |
| 资料没有电话 | 明确说明没有，不编造号码 | 明确说明未提供，不编造号码 | 未运行此题 |

本次实际12次模型调用、8217 tokens，约27.22秒；这是单轮观察，不是性能基准。逐题对照原文、最终回答、来源ID和工具轨迹后，由Codex标记 `reviewed_pass_synthetic_scope`，不是独立人工评审。框架的跨文档回答用分号合并了题目要求的两句，作为表达格式观察保留，事实和来源符合验收要求。

脚本中的 `make_cases` 只读取固定合成fixture并构造同一份RAG上下文；`run` 顺序运行两种入口，`observed_generate` 记录真实成功/失败调用元数据并计数，`calculator_only` 限定真实工具执行。意外关键词MCP请求也被阻断。预建Agent另用已学习的 `ModelCallRecorder` 记录模型步骤，不伪造其上游HTTP状态。

报告记录起始Git版本与源文件SHA256，以标识当时尚未提交的实现；不把后来的提交哈希倒写成执行时版本。全局上限27次模型调用，SDK重试关闭；实际用了12次，没有模拟模型输出、额外自动重试或改动真实配置。

本次RAG题使用应用预先构造的相同上下文，不包含Embedding或检索；没有运行数据库、正式HTTP路由或部署验证。真实超时/非法参数没有人为注入，这些失败边界仍由离线测试证明。单轮合成题通过不代表所有输入等价或稳定准确率。

## 保留哪些差异

1. **参数文本**：项目结果保留原始工具参数；框架发送下一轮消息时可能重新序列化 JSON。出站参数检查含义与调用 ID，不要求空白字节完全一致。
2. **计时范围**：原生入口计时覆盖请求与解析；框架适配还包含客户端创建/关闭和框架处理。只核验耗时非负，不比较谁更快，不能据本轮测试给出性能结论。
3. **异常原因链**：原生项目异常通常直接来自 HTTPX；框架链路还经过 SDK 和框架异常包装。项目层分类可以相同，底层异常类及链条不同。
4. **停止时机**：原生循环在最后一次模型响应仍请求工具时，会先因预算不足停止，避免执行无法回传的工具动作。当前预建 Agent 的 ModelCallLimitMiddleware 在下一次模型调用前检查，不能视为相同的工具执行前保护。
5. **返回结构**：原生/适配组合提供业务结果和部分失败记录；当前预建 Agent 包装返回消息轨迹，外部回调保留观察数据。观察数据不等同于完整项目持久化契约。
6. **非流式边界**：项目结果适配器的 HTTP 钩子会 `aread()` 缓冲响应，用于非流式协议观察。独立流式入口采用无此缓冲钩子的路径，见下节。

SDK 字段默认值、工具参数格式和提示词内容等也可能影响真实请求。本轮仅对表中固定场景作有限验收，不承诺所有输入都等价。

## 流式接口补充

[langchain_streaming.py](../app/services/langchain_streaming.py)复用已有模板，以 `chain.astream()` 读取模型流并逐个 `yield AIMessageChunk`。外层调用得到异步生成器，开始迭代才执行函数体并请求模型；它不返回完整 `LLMResult` 或业务HTTP响应。

这里的完成范围是独立函数的实现、带读与验收：已接真实模型服务，能够供Python消费者调用。尚未接入正式 `/chat`、浏览器逐段展示、取消交互或流式数据库记录；应用SSE接线仍在阶段10。阶段8收口不表示整个聊天应用已迁移为LangChain或已经提供流式产品功能。

`_open_streaming_chain` 是本项目帮助函数，标准库 `@asynccontextmanager` 让它在 `async with` 中交出链并管理客户端；其 `yield` 交出资源一次。业务函数的 `yield chunk` 则逐个交出数据。标准库 `aclosing` 在退出代码块时关闭底层迭代器；主动提前停止的消费者也应关闭外层生成器。

空正文片段仍可能携带其他字段，核心函数原样转交；消费者可以用消息片段的 `+` 合并正文及元数据。`stream_usage=True` 请求服务提供统计，业务不应假设所有服务必然提供usage。已交付前缀由消费者持有，中途异常继续向外传播，不能把前缀当作成功最终回答入库。

[两条离线测试](../tests/test_langchain_streaming.py)使用真实SDK解析按需产出的上游SSE字节流：正常场景检查文字在结束事件前可见、stop/usage保留、仅一次请求及资源关闭；中断场景检查HTTP200后的读取超时仍抛出异常、前缀保留、没有伪造最终usage且资源关闭。它们验证模型服务→Python这一段；阶段10再实现本服务→浏览器的SSE。

2026-11-04，用户参考补写后目标 **2 passed**、全量 **148 passed**。独立静态复核未发现当前契约下有意义的问题，复核者未运行测试或模型。参考补写不记为独立设计，测试通过也不等于所有概念已完全掌握。

随后沿用已授权的真实配置验收方式运行[单次探针](../playground/langchain_stream_probe.py)，[报告](../playground/results/langchain_stream_probe_2026-11-04.json)经Codex复核为 `reviewed_pass_synthetic_scope`：一次HTTP请求，73个片段（8个含正文），输出准确为“青榆/流式/验收完成”三行，收到stop及134 tokens统计。片段数、正文片段数、Token数与请求次数是不同观测量。

探针的请求钩子只计数且最多允许一次请求，不读响应正文；消费端逐片段记录合成内容与到达时间并用 `+` 聚合。使用 `aclosing` 关闭外层生成器；异常时仅保存异常类型与已有前缀，不冒充成功。报告保留执行时Git基线及源文件指纹，不记录密钥/上游异常正文或推理正文。

本次真实服务只验证正常流，未人为注入超时；中断边界和关闭行为来自离线测试。没有工具流式执行、业务持久化、服务SSE端点或浏览器验证，单轮片段时间也不是稳定延迟或性能基准。

## 我的理解

已在前面讨论中确认：整个模型响应协议合法、只有工具参数字符串非法时，保留成功模型调用，由工具处理层报告参数错误。

待补充自己的表述：框架替我们封装了哪些重复工作；为什么接入既有应用后仍需要项目适配层；哪种失败适合沿原生代码定位，哪种需要继续追踪 SDK/框架。
