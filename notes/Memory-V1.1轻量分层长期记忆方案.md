## 1. 方案定位与目标

为 agent-lab 实现基于 SQLite 的轻量分层长期记忆系统：

```text
原生 Python
+ SQLite KV 记忆
+ 显式保存与按需 LLM 结构化提取
+ 核心记忆默认注入
+ 普通记忆按 key / 问题类别选择
```

用户提出借鉴 Hermes Agent、OpenClaw 的分层思想；本项目按下述明确契约自行实现，不以复刻这些项目为验收目标，也不依赖其框架。

目标能力：

1. 自动识别用户对话中值得长期保存的信息。
2. 同一用户的新会话可使用已有用户级记忆。
3. 核心信息默认注入，普通信息按当前问题选择。
4. 用户改变偏好或目标时更新旧记忆，并保留真实来源。
5. 支持显式保存、修正、检查和删除，避免错误记忆持续生效。
6. 不同用户、不同会话的记忆按归属和作用范围隔离。

“自动记忆”不等于“每轮必定调用一次提取模型”；“方案确定”不等于“功能完成”。

## 2. 技术选择与优先级

| 模块 | 已确定方案 | 优先级与边界 |
| --- | --- | --- |
| 数据存储 | SQLite，复用现有 memory 表 | P0；基础存储已验证 |
| 提取器 | LLM 提出候选，Pydantic 校验结构，业务规则决定是否写入 | P0；结构、提取调用和上下文绑定已离线验证，持久化与聊天接线待实现 |
| 提取触发 | 显式请求 + 轻量规则触发 | P0；不默认每轮提取 |
| 作用范围 | user / conversation | 存储与来源约束已验证，读取与注入待实现 |
| 核心记忆 | 固定高价值 key，设置总长度上限，默认注入 | P0，待实现 |
| 普通记忆 | 按 key / 当前问题类别选择，限制注入数量和长度 | P0，待实现 |
| 冲突处理 | 同 key 会话级覆盖本次使用的用户级默认值 | P0；读取合并待实现，不删除用户级原记录 |
| 更新 | UPSERT + 来源追踪 + 更新时间 | 部分完成；写入函数已验证，自动提取与请求链尚未接通 |
| 管理与删除 | 显式保存、修正、用户检查、显式删除与防重建 | 管理分步接入；删除与防重建为 P1 |
| 检索升级 | 必要时评估 FTS5 全文检索或 Embedding 语义检索 | 后续，不是第一版依赖 |

术语说明：FTS5 提供全文检索，不能直接等同于基于 Embedding 的语义检索。见 [SQLite FTS5 官方说明](https://www.sqlite.org/fts5.html)。

## 3. 保留现有数据模型

现有 memory 表字段：

| 字段 | 用途 |
| --- | --- |
| memory_id | 记忆记录标识 |
| scope | user 或 conversation |
| scope_id | 对应的用户或会话标识 |
| key | 结构化记忆类别 |
| value | 当前记忆内容 |
| source_message_id | 关联真实用户消息 |
| updated_at | 本次更新的时间 |

已有唯一约束为 `(scope, scope_id, key)`；同组合更新 value、source_message_id、updated_at，不影响其他范围、归属或 key。

现有 `upsert_memory()` 使用 INSERT SELECT 筛选有效来源，再执行 UPSERT：

- 来源必须是 role=user 的真实消息。
- 用户级来源消息所在会话必须属于目标用户；允许该用户不同会话的消息作为来源。
- 会话级来源消息必须属于指定会话。
- 零写入时抛出 ValueError，原有记忆不被覆盖。
- 写入函数不自行 commit，事务由调用方控制。

继续复用 conversation、message、model_call 和 memory，不推倒重建。提取或删除需要的新状态是否落库，必须在对应小主题中明确，不能假定现有 memory 表已经具有防重建能力。

## 4. 范围与层级是两个独立维度

### 4.1 作用范围

| scope | 作用范围 | 示例 |
| --- | --- | --- |
| user | 同一用户跨会话共享 | 用户的长期学习目标、默认回答偏好 |
| conversation | 仅指定会话有效 | “这个会话中都请详细解释” |

同 key 冲突时，当前会话的值优先用于本次上下文；用户级原记录仍然保留，其他会话继续使用各自的有效记忆。

“这次回答详细一点”是当前请求要求，不能自动扩展成整个会话的持续偏好；当前问题本身已进入模型输入，无须为使本轮生效而保存长期记忆。

匿名会话不能写入或读取用户级记忆；已有可选 user_id 和会话归属检查不等于已经实现身份认证。

### 4.2 注入层级

| 层级 | 选择策略 | 示例 |
| --- | --- | --- |
| Core Memory | 少量稳定、高价值 key，在预算内默认注入 | 回答风格、语言偏好 |
| Regular Memory | 按当前问题类别和 key 选择 | 学习目标、项目进度、历史经历、技术偏好 |

第一版通过固定 key 映射区分 Core / Regular，不立即增加层级字段或额外 scope。候选 key 白名单已在 5.2 确定；Core / Regular 分类映射、长度与条数上限仍需在选择与注入实现前明确。本节举例说明层级，不额外扩展候选 key 白名单。

“核心记忆常驻”指每次组装模型上下文时按规则读取并注入，不表示数据库内容能自动进入模型，也不表示模型永久保存了这些信息。

## 5. 触发、提取与写入

### 5.1 触发策略

- 明确的记忆保存、修正或删除请求及时处理；具体识别方式和执行时序在对应小主题确定。
- 普通聊天正常完成后，经轻量规则判断有提取价值时再调用 LLM。
- 普通聊天、临时要求和无价值内容允许跳过，不为“自动记忆”而每轮额外调用模型。
- 不默认反复扫描全部历史；历史重提取与删除后的防重建必须统一约定。
- 用户明确要求不要保存的内容不写入，不能把模型猜测当成用户确认事实。

2026-10-21 已明确首个门控函数契约：`app/services/memory.py` 中的 `should_extract_memory(message: str) -> bool` 只看当前用户消息，返回是否值得进入提取流程，不执行 HTTP 或数据库操作。

| 代表输入 | 是否触发 |
| --- | --- |
| 记住，以后默认用中文回答。 | True |
| 解释一下 Python 装饰器。 | False |
| 这次详细一点，以后默认简洁一些。 | True |
| 不要保存这条消息，我的学习目标是开发 Agent。 | False |

本条不保存要求优先于正向线索；不能仅因包含“这次”就否决整条消息中的长期偏好。这是有限规则的预筛选契约，后续 LLM 仍可返回 skip；不将关键词匹配当成完整语义理解或保存授权。

### 5.2 候选输出与职责

2026-10-21 已明确第一版提取结果契约：一个结果可包含多条待写入记忆，整体 action 为 upsert 或 skip。模型放在 app/schemas.py，使用 MemoryCandidate 描述单条候选、MemoryExtractionResult 描述整个结果。

```json
{
  "action": "upsert",
  "memories": [
    {
      "scope": "user",
      "key": "learning_goal",
      "value": "学习 AI Agent 开发"
    }
  ]
}
```

无候选时允许输入 `{"action": "skip"}`。模型中的 memories 使用独立的默认空列表，因此该输入归一化为 action=skip、memories=[]；skip 不允许携带非空记忆列表。upsert 必须携带非空列表，缺失或空列表都属于校验失败。

单条候选仅允许 scope、key、value：scope 为 user / conversation，key 暂定固定为 answer_language、explanation_style、learning_goal、tech_stack，value 去除首尾空白后必须非空。候选与整体结果均拒绝额外字段，不接受模型指定 scope_id 或 source_message_id。匿名用户级候选等依赖当前请求的业务校验留到后续接线。

2026-10-21 已完成正确 RED → 用户手写模型与关键断言 → GREEN → 复述收口：修正 learning_goal 拼写后，目标 3 passed、全量 51 passed；已澄清嵌套列表与元素类型、独立默认列表、ValueError 包装和 return self 的返回链。这里只验证提取结果结构，不代表 LLM 提取、业务范围校验或持久化已经接通。

2026-10-21 提取调用小主题的局部契约：

- `extract_memories(message: str) -> MemoryExtractionResult` 为异步函数，接收当前用户消息；由调用方决定是否触发，不在函数内部重复执行轻量门控，不读写数据库。
- 复用现有 generate_reply 的 HTTP 传输与模型配置；为其增加可选的专用系统指令参数，默认聊天指令保持原行为。提取调用不携带旧历史或工具声明，不引入新模型依赖。
- 先由现有 LLM 层解析外层响应，再由 `MemoryExtractionResult.model_validate_json` 解析和校验模型正文字符串。只验证结构，不声称约束解码或真实模型语义判断已经通过。
- 本小主题保留原有 LLMRequestError 和 Pydantic ValidationError 作为失败信号；合法 skip 是正常结果，解析失败不能转换成 skip。后续聊天接线由调用方捕获预期失败并记录安全元数据，不向正常聊天传播失败，也不保存无效候选。该失败隔离尚未接通。

2026-10-24 实现验证：用户手写 generate_reply 的 keyword-only system_prompt 参数与 extract_memories。专用指令通过同一 HTTP 请求链发出，模型正文交给 model_validate_json；目标测试 2 passed、全量 57 passed。验证使用 fake HTTP，保护专用指令传递、当前用户消息、候选解析去空白和非 JSON 正文拒绝；不证明真实模型会遵守指令或正确判断记忆价值。业务范围校验、写入、聊天失败隔离与保存确认仍未接线。

职责分配：

1. LLM 识别候选动作、内容、key 和建议 scope。
2. Pydantic 校验允许字段、类型、动作、范围、key 及内容约束；结构有效不代表语义一定正确。
3. 业务规则决定是否允许保存、更新或跳过，并处理临时要求和匿名范围等限制。
4. 应用根据本轮已验证的请求和会话绑定 scope_id、source_message_id、updated_at；不接受模型任意指定身份或来源消息 ID。
5. 数据库继续执行来源与归属约束，并由调用方提交短事务。

### 5.3 普通对话的目标执行顺序

```text
请求校验与会话归属检查
  → 读取已有记忆，合并范围并选择 Core / Regular
  → 沿现有链路读取历史、保存本轮用户消息并提交
  → 关闭数据库连接，调用原生 Agent 生成回答
  → 保存回答与主聊天调用记录并提交，关闭连接
  → 判断本轮是否需要提取记忆
      → 不需要：跳过
      → 需要：限时调用提取器，校验候选
          → 独立短事务新增或更新记忆
  → 返回回答
```

这是目标链路，读取函数和提取器尚未接通。明确记忆操作的专门分支不能机械套用“普通聊天结束后再处理”，须先确定它是否需要在本轮回答前完成及如何反馈结果。

记忆读取发生在回答前；新记忆写入成功后供后续请求使用。第一版允许在正常回答成功后同步执行按需提取，因此触发提取的请求会增加客户端等待时间。

不把网络等待放进长期持有的数据库事务。后台执行留作后续优化；提前返回 HTTP 响应本身不能证明记忆任务获得了可靠执行、重试或完成保证。

### 5.4 两类模型调用、独立结果与保存确认

2026-10-21 经讨论明确以下设计；本节是后续实现的约束，不代表聊天接线已经完成。

普通聊天调用负责回答用户，记忆提取调用负责生成程序可处理的候选。这是两个不同任务；无工具、无重试且触发提取时，通常分别调用模型一次。主 Agent 若进入工具循环，自身仍可能多次调用模型，不能把整轮 Agent 与单次 HTTP 模型调用混为一谈。

| 调用 | 输入与目标 | 输出交给谁 |
| --- | --- | --- |
| 主聊天 | 当前问题与允许的上下文；回答问题 | 应用保存正常回答，再返回用户 |
| 记忆提取 | 第一版只提供本轮用户消息与专用提取指令；识别候选 | 应用校验并决定写入，不把候选 JSON 当作聊天回答 |

不把助手自己生成的回答当作用户事实的来源；身份和来源消息 ID 仍由应用绑定。

分别看普通聊天的五种情况；表中“聊天成功”指正常回答已经生成并保存提交：

| 情况 | 记忆处理 | 对用户的结果 |
| --- | --- | --- |
| 主聊天失败 | 不进入普通聊天后的提取流程；记录真实聊天失败 | 按现有错误映射返回，例如超时 504 |
| 聊天成功，轻量规则未命中 | 不调用提取模型 | 返回正常回答，不宣称新记忆已保存 |
| 聊天成功，规则命中，提取返回合法 skip | 正常无候选，不写 memory | 返回正常回答，不追加保存成功确认 |
| 聊天成功，提取返回合法 upsert，业务校验及提交成功 | 保存或更新 memory | 返回正常回答；需要确认时由应用补充实际保存结果 |
| 聊天成功，但记忆处理失败 | 捕获预期的提取、校验或写入失败，记录安全失败元数据，不保存无效候选 | 保留正常回答；显式保存请求应如实说明未能保存 |

正常回答保存失败不满足“聊天成功”前提，不进入后置提取流程，不能把它当成记忆支线失败后返回成功。

轻量规则允许误命中。例如“以后 Python 会取代 Java 吗？”包含“以后”，但没有用户长期偏好或目标，提取模型可正常返回 `{"action":"skip","memories":[]}`。这是成功判断没有候选；正文是“好的，我记住了”等非 JSON 文本则是提取失败，不能转换为 skip。

外层上游响应与正文 JSON 是两层：LLM 层通过 response.json() 解析外层，再取 choices[0].message.content 得到正文字符串；提取器通过 model_validate_json 解析并校验正文。上游 HTTP 200、外层 JSON 合法，不代表提取正文合法。

提取器通过异常向应用调用方报告失败；应用在记忆支线捕获后记录失败，并继续返回此前已成功的聊天回答。异常不是交给“会话对象”，也不会自动要求整个 HTTP 请求失败；主聊天自身失败仍按原错误边界处理。失败记录只保留分类、状态、耗时等安全元数据，不直接打印可能包含模型正文的校验异常详情。

保存确认由应用依据实际提交结果生成，不需要为了追加“已保存你的中文回答偏好”再调用一次模型。只有候选校验、业务校验与数据库写入并提交成功后，才能追加成功确认；skip、未触发和失败均不能追加。聊天模型自行声称“记住了”不能作为保存成功的证据；显式记忆分支应由应用控制操作确认，避免提前承诺。

若确认文案被拼接进最终回答，最终返回文本与持久化的 assistant 消息应保持一致；在聊天接线时明确最终组装与持久化的顺序，不能只改返回字符串而遗漏历史记录。当前 ChatResponse 仍只有 conversation_id 和 answer，本小主题不提前修改响应结构或实现确认拼接。

### 5.5 候选绑定与匿名范围校验

2026-10-24 用户已选择整批拒绝：匿名请求只要含一条 user 范围候选，本批候选全部拒绝，不保留其中合法的 conversation 候选，也不自动降级范围。相比部分接受，第一版不引入部分成功结果与反馈状态。

本小主题的局部接口设计由 Codex 提出，复用现有原生 Python 分层：

- 在 app/services/memory.py 增加同步纯函数 `prepare_memory_writes(extraction, *, user_id, conversation_id, source_message_id)`，接收已通过 Pydantic 校验的 MemoryExtractionResult 和应用提供的请求上下文。
- 返回 `list[MemoryWrite]`。MemoryWrite 为内部 dataclass，字段为 scope、scope_id、key、value、source_message_id，表达待写入数据，不代表已经持久化；不扩展模型候选 Schema，不新增数据库列。更新时间由后续写入调用方提供。
- user 候选绑定请求上下文中的 user_id，conversation 候选绑定 conversation_id；所有待写入项绑定本轮同一个 source_message_id。模型不能提供或覆盖这些身份与来源字段。
- 匿名请求含 user 候选时抛出 ValueError，不返回部分结果；匿名请求只有 conversation 候选时正常绑定。合法 skip 返回空列表。
- 本函数不调用 LLM、不查数据库、不执行写入。它只绑定应用提供的上下文，无法凭 ID 证明来源存在或归属正确；已有 upsert_memory 继续在真实数据库中验证来源与范围归属，后续接线调用方负责事务提交。
- 验证范围为有用户的混合范围绑定、匿名会话级绑定与匿名混合候选拒绝。纯函数拒绝整批结果不等于 SQL 批量写入原子性已验证；实际批次写入与回滚留到持久化接线主题。

## 6. 选择、合并与上下文注入

读取流程：先限制为当前用户和当前会话可见的记忆，再按 key 合并范围、区分 Core / Regular 并应用注入预算；不能先混合不同用户的数据再依靠 Prompt 隔离。

逻辑消息顺序：

```text
System：Agent 基础指令
Memory Context：核心记忆 + 与当前问题相关的普通记忆
History：最近 10 条聊天消息
User：当前问题
后续按既有 Agent 循环追加工具请求与工具结果
```

Memory Context 是应用明确标记的参考数据，不是高优先级命令，不得覆盖系统安全要求或当前用户明确的要求。它应独立于历史消息传递，具体消息角色和封装方式在注入小主题确定；不能因写了一个 Memory Context 标题就认为协议已经提供了新的消息角色或权限层级。

没有相关普通记忆时不强行填充；没有任何记忆时保持现有聊天路径兼容。Core 也必须受总长度限制，Regular 同时受条数和长度限制。

## 7. 更新、检查、删除与失败隔离

### 7.1 更新与管理

- 同范围、同归属、同 key 改口时更新当前值、来源和时间。
- 会话级覆盖不删除用户级默认值；删除会话级值后是否恢复显示用户级值，要在删除契约中明确并测试。
- 用户能检查实际保存的内容、范围和来源，并显式要求修正或删除；具体接口和路由尚未确定。
- 删除与防重建为 P1，不能因为物理删除一行就宣称已经防止从旧消息重建。
- 删除 memory 记录不等于擦除 message 历史；仍在最近消息窗口中的原始信息可能继续被模型看到，验收要区分“停止注入长期记忆”与“所有上下文立即遗忘”。

防重建所需的处理策略、是否需要删除标记或提取边界状态、删除后允许用户重新明确保存的条件，在删除实现前集中确定，不预先将某一种机制记为已完成。

### 7.2 失败处理

- 提取超时、响应不可解析、候选无效或记忆写入失败，不把已经成功的正常聊天改成失败响应。
- 回答持久化与记忆写入使用分开的事务边界；记忆事务失败不能回滚已经提交的正常聊天。
- 记忆读取失败时的回退行为与异常边界需在读取接线时明确，不能借“失败隔离”掩盖用户范围混用。
- 显式操作失败时如实反馈，不能回答“已记住”或“已删除”。
- 保留可排查的错误分类和必要元数据，不记录 API Key、Authorization Header、完整用户消息、完整模型回答或原始上游正文。
- 提取调用的耗时、结果和失败记录如何与主聊天区分，在接线前确定；不能把它误算成主 Agent 工具循环的一次调用或虚构正常回答的失败记录。

## 8. 与历史消息和 RAG 的边界

| 模块 | 职责 |
| --- | --- |
| message 表 | 持久化用户消息与最终助手回答 |
| 最近 10 条消息窗口 | 保持当前会话的上下文连续 |
| memory 表 | 保存经校验的结构化稳定信息，支持跨轮次和跨会话选择 |
| 后续原生 RAG | 检索 Markdown、PDF 等外部知识文档并返回来源 |

保留最近消息窗口，记忆不替换完整聊天记录，也不把 RAG 文档检索和用户偏好记忆混为一个模块。记忆 P0 完成不等于阶段 7 的原生 RAG 或整个阶段已经完成。
