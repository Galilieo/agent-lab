# 04 评测方案

日期：2026-11-16。状态：设计方案，尚未实施。评测集规模是起点，按标注成本和结果稳定性调整。所有结果都要写明样本量、标注方式、模型版本和失败案例；不预设目标分数。

## 1. 原则

1. **先有评测集，再调功能。** 每个 P0 功能开发前，先准备至少一个小评测集。
2. **离线评测与线上指标分开。** 离线评测证明设计有效；线上指标反映真实使用情况。两者不能互相替代。
3. **开发集与测试集分开。** 提示词、阈值只在开发集上调整；测试集只用来报告最终结果。
4. **记录失败案例。** 每次评测保存全部输入、输出和判定，便于回看；不只报总分。
5. **对照实验一次只改一个变量。**
6. **沿用现有做法。** 参考[固定评测与结果判读](../固定评测与结果判读.md)：结果写入独立文件，不覆盖历史记录；默认 pytest 不跑需要真实模型的评测。

## 2. 数据来源与隐私

| 数据 | 来源 | 注意 |
| --- | --- | --- |
| JD | 用户自己从公开招聘页面复制 | 仓库中**不提交 JD 原文**，只提交标注结果和来源链接；原文存在本地私有目录（加入 .gitignore） |
| 简历 | **合成简历**为主：按不同水平（优秀 / 一般 / 薄弱）、不同方向编写 | 不使用真实他人简历；如果使用自愿提供的真实简历，必须脱敏并取得同意，且不提交到仓库 |
| 面经与八股 | 用户自己整理的内容 | 不抓取第三方平台 |
| 注入样本 | 自己编写 | 可以公开提交 |

## 3. 离线评测集

### E1 简历事实拆分（V1）

- **规模：** 20 份合成简历。
- **标注：** 每份简历人工写出应有的事实清单。
- **指标：** 事实召回率（应有的事实是否都拆出来）、错误率（拆出的事实与原文不符的比例）、数字事实的准确率、职责程度初判的准确率（标注时同时标出每条事实的职责程度）。
- **判定：** 事实对应关系由人工判定；可以先用模型做初步匹配，再人工复核。

### E2 JD 解析（V1）

- **规模：** 50 份 JD，开发集 20、测试集 30。覆盖 AI 应用、后端、前端、算法等方向，以及写法规范和写法混乱的 JD。
- **标注：** 硬性要求、加分项、技术关键词（标准化后）。
- **指标：**
  - 关键词：精确率、召回率、F1
  - 要求条目：召回率；硬性要求与加分项的分类准确率
  - 基本字段（地点、时长）：准确率；JD 没写时是否正确留空，不猜测

### E3 匹配判断（V1）

- **规模：** 10 份合成简历 × 5 份 JD = 50 组，大约 400～600 条要求判断（实际数量取决于 JD）。
- **标注：** 每条要求标注「已覆盖 / 部分覆盖 / 未覆盖」，以及依据的事实 ID。
- **指标：** 三分类一致率、各类别的混淆矩阵；「已覆盖」判断中依据事实是否正确。「表达缺口」由程序从「已覆盖」和事实来源派生，不单独标注，由单元测试保证。
- **标注一致性：** 抽 50 条请第二个人标注，计算两人一致率；如果人和人之间都不一致，说明标注标准需要修改。

### E4 依据检查器（V1，核心）

目的：测量检查器能不能发现编造。

- **构造方式：** 取 E3 中的事实，写出改写句子，并人工植入已知类型的编造（见 [03 第 1.1 节](./03-可信安全与隐私.md#11-要防止什么)的六种类型），同时保留一批没有编造的正常改写。
- **规模：** 300 句左右，正常与编造各半，每种编造类型不少于 20 句。
- **指标：**
  - 编造检出率（召回）：有编造的句子被拦下的比例
  - 误拦率：正常句子被误判为编造的比例
  - 按编造类型、按检查层次分别统计，找出哪一层抓住了什么
- **对照：** 只用第一层；一 + 二层；一 + 二 + 三层。

### E5 端到端编造率（V1，主要报告指标）

- **方法：** 用 E3 的 50 组「简历 × JD」跑完整改写流程，人工检查每条最终输出有没有编造。
- **指标：** 编造率 = 含编造的条目数 ÷ 总条目数；回退率 = 被回退为原文的条目比例（反映改写成功率）。
- **对照（一次只改一项）：**

| 版本 | 说明 |
| --- | --- |
| A | 直接让模型按 JD 改写简历全文（基线） |
| B | 改为逐条改写并要求引用事实 ID |
| C | B + 第一、二层程序检查与修订 |
| D | C + 第三层模型检查 |

同时记录每个版本的平均 token 和耗时，说明可信度提高的代价。

### E6 改写质量盲评（V1，主观）

- **方法：** 选 10 组，原简历与改写简历随机排序，请 3～5 位同学盲评「哪份更适合这个岗位」，并给出理由。
- **报告：** 偏好比例与样本量。样本小，结论要说明局限，只作为参考。

### E7 提示注入（V1 基础，V3 专项）

- **构造：** 在 JD 中植入多种注入（直接指令、伪装成要求、角色扮演、零宽字符隐藏、中英文混合），共 50 条起。
- **攻击成功的定义：** 例如改写结果出现了注入要求加入的技能，或匹配报告被注入改变结论。
- **指标：** 攻击成功率、检测命中率、正常 JD 的误报率。
- **对照：** 无防护；提示词隔离；加检测；加结构兜底。

### E8 长期记忆（V2）

- **方法：** 编写 20 个多会话脚本，例如「第 1 次会话说目标城市是上海，第 3 次改为杭州，第 5 次询问推荐」。
- **场景类型：** 跨会话召回、改口后更新、删除后不再出现、无关记忆不注入、记忆不进入简历改写。
- **指标：** 各场景通过率；最后一项必须 100%，并由程序测试保证。

### E9 面经检索（V2）

- **方法：** 50 个查询（例如「Agent 开发实习，RAG 方向常问什么」），人工标注相关文档。
- **指标：** Recall@5、MRR。
- **对照：** 纯向量（基线）；加 jieba 分词的 Postgres 全文检索并用 RRF 融合。融合版本明显更好才保留。
- **附带验证：** 带 user_id 过滤时，前 k 条结果是否召回不足。

### E10 模拟面试评分（V2）

- **校准：** 30 段面试回答，由用户和至少一位同学按评分标准人工打分；比较模型评分与人工评分的一致性（例如分档一致率）。
- **追问质量：** 抽 50 次追问，人工判断是否针对用户回答的内容，而不是泛泛提问。
- **对照（V3）：** 单 Agent 与「面试官 + 评分员」两个 Agent，比较评分一致性、追问质量和花费。

### E11 上下文管理（V2）

- **方法：** 用同一批模拟面试脚本（例如 10 场，每场 15 轮以上），比较两种上下文策略。
- **对照：** 保留全部历史；已结束考察点摘要 + 当前考察点完整问答。
- **指标：** 追问是否针对用户回答（人工抽检）、是否重复提问已问过的内容、平均每轮 token。
- **目的：** 说明摘要策略省了多少成本、质量有没有下降。

## 4. 使用记录与线上指标

**V1 个人使用阶段**只记录本人的使用情况：处理了多少份 JD、生成了多少份定制简历、改写条目的接受率、需要手动修改的事实比例、遇到的问题与改进。这些可以写进 README，作为「本人实际使用」的证据。

下表是以后开放给他人时的指标：

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 注册用户数 | 完成注册的人数 | 规模 |
| 激活用户数 | 至少完成一次「贴 JD → 定制简历」的人数 | 核心流程是否走得通 |
| 7 日留存 | 注册后第 2～7 天内再次使用的比例 | 是否真的有用 |
| 定制完成率 | 导出数 ÷ 改写运行数 | 结果是否可用 |
| 条目接受率 | 用户接受的改写条目比例 | 改写质量 |
| 事实修改率 | 用户修改的拆分事实比例 | 解析质量 |
| 好评率 | 点赞 ÷ 全部评价 | 满意度 |
| 每次运行成本 | 平均 token 与费用 | 成本控制 |
| 失败率 | 各 purpose 的模型调用失败比例 | 稳定性 |

用户少时，比例指标波动很大，报告时同时写出分子和分母。

## 5. 评测工程

```text
evals/
├── datasets/          # 标注数据（不含 JD 原文与真实简历）
├── private/           # 本地原文，不提交（.gitignore）
├── runners/           # 每个评测一个运行脚本，支持 --output 指定结果文件
├── results/           # 每次运行的完整记录：输入、输出、判定、模型版本、提示词版本
└── reports/           # 汇总表与失败案例分析
```

- 每次运行记录：评测集版本、代码提交号、模型名称、提示词版本、参数。
- 程序判定部分（第一、二层检查、记忆隔离）写成普通 pytest；需要真实模型的评测用单独命令运行。
- 模型做裁判的评测，保留裁判的输入与输出，并定期人工抽查。

## 6. 第一版要拿出的结果

V1 完成时，README 至少包含：

1. E2 JD 解析的 F1。

4. 每项评测的样本量、标注方式和主要失败类型。
