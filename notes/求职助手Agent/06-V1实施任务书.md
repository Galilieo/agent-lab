- 按 purpose（如 `extract_facts`、`parse_jd`、`order_ocr`、`match`、`plan`、`rewrite`、`ground_check`、`agent`）配置：模型名、是否开启思考、temperature、max_tokens、是否 JSON Output（见 D2）。
- 预算：调用前检查本次运行的剩余调用次数与 token；不足时抛出明确异常。
- 重试：只对超时、连接错误、上游 5xx 有限重试（思路沿用现有 `model_retry.py`）。
- 结构化输出：JSON Output + Pydantic 校验；校验失败带着错误信息重试一次，仍失败则报错。
- 记录：每次调用（含失败）写入 `model_call` 表：purpose、模型、结果、耗时、token。
- 不可信内容：提供统一函数，把不可信文本包进带明确分隔标记的数据区块。

**验收：** 用假客户端测试重试、预算耗尽、JSON 校验失败后修复、调用记录写入；另写一个显式运行的脚本，用真实 DeepSeek 跑一次 JSON 输出，确认参数可用。

### T1.2 Prompt 文件与版本

- `prompts/` 下每个 prompt 一个文件，文件头写 `version`。
- 加载函数返回内容和版本号；网关调用时把版本号写入 `model_call`。

**验收：** 修改 prompt 后版本号变化能体现在调用记录里。

### T1.3 登录与用户隔离（只做后端）

按 D1（自写最小登录）实现：

- 注册、登录、登出、获取当前用户四个接口。
- 登录成功时生成随机 token，数据库只存它的 SHA-256；Cookie 设置 HttpOnly、SameSite=Lax、有效期。
- `current_user` 依赖：从 Cookie 取 token，查有效 session，返回用户；待删除状态的用户只允许访问「恢复账号」。
- 隔离测试框架：准备用户 A、B 两组数据，参数化遍历所有业务接口，断言 A 读、改、删 B 的资源都返回 404。之后每加一个接口，都要加进这个列表。

**验收：** 登录流程测试通过；隔离测试框架就绪（此时业务接口还少，后续逐步补全）。

### T1.4 简历上传与经历事实库（F1）

- 迁移：`resume_document`、`fact_set`、`fact` 表（全部带 `user_id`）。
- 解析：按 [01 F1「输入格式」](./01-功能设计.md#输入格式2026-11-16-扩充)支持 PDF、DOCX、TXT、Markdown、HTML、图片和粘贴文本。PDF 提取不到文字时用 pypdfium2 渲染成图片再 OCR；图片和扫描件的识别结果先返回给前端让用户核对，确认后才拆分事实。上传文件解析后不保存。同时保存简历的分段结构（`sections_json`），供 F5 组装完整简历。
- OCR：`services/parsing.py` 封装 RapidOCR，提供 `POST /api/ocr`。多张图片按 [01 F1「多张截图的整理」](./01-功能设计.md#多张截图的整理简历与-jd-共用2026-11-16)处理：逐张识别 → 网关新增用途 `order_ocr`（非思考模式、JSON Output）只输出顺序 → 程序校验顺序是合法排列、拼接并去掉相邻重叠行；失败时退回上传顺序。
- 测试：OCR 用一张自带的合成截图，只断言能识别出几个关键字；排序用假的模型客户端，覆盖正常排序、非法顺序（重复或缺编号）退回上传顺序、重叠行去重、单张图片不调用模型。
- 事实拆分：通过网关调用模型，输出符合 Pydantic 模型的原子事实列表（经历、类型、职责程度、内容、是否含数字、原文片段）。
- 原文校验：来自简历的事实保存 `source_quote`，程序校验它确实是简历原文的一段（去掉空白后比较），结果写入 `quote_verified`；未通过的事实不能确认，返回「需要用户核对」。
- 矛盾规则：同一类字段（成绩、日期、同一段经历中的数字）出现不同值时标记为矛盾，返回给调用方，由第 3 周的 `ask_user` 向用户提问。职责程度用 Enum（lead / own / participate / na）；原文没有明确说法时默认 participate，并在返回结果里标记「需要用户核对」。
- 接口：按 [02 第 6 节](./02-技术架构与数据模型.md#6-接口v1)实现上传、查询、修改、确认、补充、删除、提交新版本。
- 规则：只有已确认的事实能进入提交的版本。

**验收：** 用合成简历走通「上传 → 拆分 → 修改确认 → 提交版本」；未确认事实与原文校验未通过的事实不进入版本的测试通过；矛盾规则有单元测试；接口加入隔离测试。

### T1.5 JD 解析与岗位库（F2、F10）

- 迁移：`job_posting`、`user_job` 表（02 第 5.1 节）。V1 的 job_posting 全部为 private，按 owner_id 隔离。
- 输入：粘贴文字，或先调用 `POST /api/ocr` 识别截图、由用户在文本框核对后再提交；两种来源走同一套解析流程。
- 输入清洗：去除零宽字符，限制长度。
- 注入检测：规则匹配常见句式（中英文），命中结果写入 `injection_flags`；只标记、不阻断。
- 结构化提取：硬性要求、加分项、职责、关键词、业务场景、基本字段（公司、地点、薪资、每周到岗、实习时长、学历、毕业时间、截止日期），每条附原文片段；JD 没写的字段留空。薪资另存换算后的「元/天」区间用于筛选，原始写法保留。
- 岗位库接口：列表（按方向、关键词、城市、薪资、进度筛选）、详情（job_posting 与 user_job 合并）、修改字段与自定义字段（写入 user_job）。
- 关键词标准化：维护一份同义词表（YAML），由程序把提取结果映射成标准名。
- 统计接口：按关键词与硬性要求计数，由程序计算。

**验收：** 注入规则、关键词标准化、薪资换算的单元测试通过；修改字段不改动 job_posting 的测试通过；接口加入隔离测试。

### T1.6 E1、E2 第一版

- E1：5～10 份合成简历的事实标注与评测脚本（事实召回、错误率、数字事实准确率）。
- E2：20 份 JD 标注（开发集），评测脚本输出关键词精确率、召回率、F1，以及要求条目召回与分类准确率。
- 结果写入 `evals/results/`，每次运行记录代码提交号、模型、prompt 版本。

**第 1 周完成标准：** 用接口能从简历得到事实清单、从 JD 得到岗位与要求清单；E2 有第一版 F1。

## 5. 第 2 周：匹配、改写、依据检查与完整简历

### T2.1 匹配报告（F3）

- 迁移：`match_report` 表。
- 模型判断每条要求已覆盖、部分覆盖、未覆盖，并引用事实 ID；程序校验引用的事实存在、属于该用户、已确认。
- 程序把「已覆盖」中引用事实全部来自用户补充（`source = user`）的条目改判为「表达缺口」，并写单元测试；硬性要求单独汇总。
- 不输出笼统的匹配度分数。

### T2.2 依据检查第一、二层（纯函数）

- 第一层：引用存在、已确认、属于本次版本、同一段经历（技能概述除外）。
- 第二层：从改写文本提取数字、技术名、组织名、角色词、程度词，与引用事实比对。角色词的等级与引用事实的 `responsibility` 字段比较；程度词（了解 < 熟悉 < 熟练 < 精通）与事实文本比较。角色词表、程度词表、同义词表放在配置文件里。
- 这是项目核心，**测试要最充分**：六种编造类型各写多个用例，正常改写也要有足够用例，防止误拦。

### T2.3 依据检查第三层（模型）

- 独立的 `ground_check` 调用，只输入「改写句子 + 引用事实原文」，非思考模式、temperature 0。
- 输出：支持、部分支持、不支持，以及不支持的片段。

### T2.4 改写流程图

- 迁移：`tailor_run`、`tailored_bullet` 表。
- LangGraph 图按 [02 第 3 节](./02-技术架构与数据模型.md#3-改写流程图v1-核心)：load_inputs → match → plan → rewrite → ground_check → revise / fallback → finalize。
- 检查点：`AsyncPostgresSaver`。自己建连接或连接池时必须带 `autocommit=True` 和 `row_factory=dict_row`（官方说明，否则建表可能不生效、读取会报错）；首次使用调用 `setup()`。
- thread_id 用 `{user_id}:{run_id}`，恢复运行前校验归属。
- 执行入口集中在一个函数：第 3 周由 `tailor_resume` 工具在对话中调用，面板的「重新生成」用进程内后台任务调用。
- 改写时每条只放入相关事实和对应 JD 要求（[02 第 11.3 节](./02-技术架构与数据模型.md#113-各场景的做法)）。

**验收：** 端到端测试（假模型）覆盖：全部通过、修订后通过、两次修订仍失败而回退、预算耗尽。

### T2.5 完整简历与导出（F5）

- 迁移：`tailored_resume` 表。改写完成后组装完整简历（接受的用改写版、不用或回退的保留原文、未改写部分原样保留）。

- 每条改写保存依据的事实编号与检查结果，供面板的「依据追溯」显示。

**验收：** 组装规则的单元测试通过；导出的 HTML 单独打开可以编辑和打印。

## 6. 第 3 周：对话 Agent

### T3.1 会话与消息

- 迁移：`conversation`、`message`、`agent_action`、`memory`、`application` 表（02 第 5.1 节）。
- 接口：会话列表、新建、获取、改标题与当前岗位、删除（02 第 6 节）。

### T3.2 Agent 图与工具（核心）

- 按 [02 第 2.2 节](./02-技术架构与数据模型.md#22-对话-agent-与工具v1-核心入口2026-11-16-新增)实现：build_context → call_model（带工具）→ 读取 / 生成类直接执行 → 写入类与提问类 `interrupt()` 暂停 → 用户决定后恢复。
- 工具按读取、生成、写入、提问四类定义；工具只接收登录态的 user_id，模型不能传入用户。
- 写入类工具先写 `agent_action`（pending），确认后执行并记录撤销信息；`POST /api/actions/{id}/undo` 实现撤销。
- `ask_user`：把第 1 周的原文校验失败、矛盾、职责程度不明，以及当前岗位缺少的关键信息合并成一张提问卡片。
- 当前岗位软绑定：第一次解析出 JD 时自动设置；再发 JD 时用提问卡片询问「新开对话 / 切换 / 保持不变」。
- 预算：每次运行的工具调用次数、token、时长上限。
- 检查点：thread_id 为 `{user_id}:{conversation_id}`，恢复前校验归属。

**验收（假模型）：** 写入类操作未经确认不改动任何数据；拒绝后不执行；撤销后数据回到原状态；工具读不到其他用户的数据；预算耗尽时停止并说明进度。

### T3.3 流式输出

- `POST /api/conversations/{id}/messages` 与 `POST /api/conversations/{id}/actions/{action_id}` 返回 SSE：`text`、`tool_start`、`tool_end`、`confirm`、`done`、`error`（02 第 2.2 节）。
- 客户端断开后运行继续，结果写入消息表。

### T3.4 上下文与记忆

- 按 [02 第 11 节](./02-技术架构与数据模型.md#11-记忆与上下文管理)拼装上下文；超出预算时把早期轮次压缩进 `conversation.summary`。
- 轻量长期记忆：`remember` 工具（写入类，需确认）；每次对话放入全部记忆；删除后防重建；改写只把写作偏好用于措辞。
- 记忆接口：查看、修改、删除。

### T3.5 轻量投递追踪（F9）

- `record_application` 工具（写入类，需确认）与 `POST /api/applications`：冻结简历快照（内容、事实库版本、HTML）。
- 进度更新；`GET /api/applications/{id}/diff`：按条目比较快照与当前简历、列出投递后事实库的变化、标出后来被回退或改弱的表述（程序计算）。

## 9. 调研中发现的注意事项

- DeepSeek 开启 JSON Output 时，prompt 中必须出现「json」字样并给出格式示例，且 `max_tokens` 要设够，否则输出可能被截断（官方说明）。
- 思考模式下 `temperature` 等参数不生效也不报错，容易误以为设置成功；网关要按用途明确设置思考开关。
- `langgraph-checkpoint-postgres` 的连接要求 `autocommit=True` 与 `row_factory=dict_row`，与 SQLAlchemy 的连接分开管理（两者都用 psycopg 3，但不共用连接）。
- Colima 在电脑重启后不会自动启动，启动脚本要先检查。
- `docker compose down -v` 会清空数据库，平时只用 `down`。
