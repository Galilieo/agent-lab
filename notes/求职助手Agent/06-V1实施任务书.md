## 4. 第 1 周：基础能力、事实库与 JD 解析

### T1.1 模型调用网关

- 位置：`services/llm_gateway.py`。
- 按 purpose（如 `extract_facts`、`parse_jd`、`match`、`plan`、`rewrite`、`ground_check`）配置：模型名、是否开启思考、temperature、max_tokens、是否 JSON Output（见 D2）。

- 结构化输出：JSON Output + Pydantic 校验；校验失败带着错误信息重试一次，仍失败则报错。
- 记录：每次调用（含失败）写入 `model_call` 表：purpose、模型、结果、耗时、token。

### T1.3 登录与用户隔离（只做后端）

- 注册、登录、登出、获取当前用户四个接口。

- 隔离测试框架：准备用户 A、B 两组数据，参数化遍历所有业务接口，断言 A 读、改、删 B 的资源都返回 404。之后每加一个接口，都要加进这个列表。

## 5. 第 2 周：匹配、改写与依据检查

### T2.1 匹配报告（F3）

- 迁移：`match_report` 表。
- 每条要求判断已覆盖、部分覆盖、未覆盖，并引用事实 ID；程序校验引用的事实存在、属于该用户、已确认。
- 不输出笼统的匹配度分数。

### T2.2 依据检查第一、二层（纯函数）

- 第一层：引用存在、已确认、属于本次版本、同一段经历（技能概述除外）。
- 第二层：从改写文本提取数字、技术名、组织名、角色词、程度词，与引用事实比对；等级表（了解 < 熟悉 < 熟练 < 精通；参与 < 负责 < 主导）与同义词表放在配置文件里。
- 这是项目核心，**测试要最充分**：六种编造类型各写多个用例，正常改写也要有足够用例，防止误拦。

### T2.3 依据检查第三层（模型）

- 独立的 `ground_check` 调用，只输入「改写句子 + 引用事实原文」，非思考模式、temperature 0。
- 输出：支持、部分支持、不支持，以及不支持的片段。

### T2.4 改写流程图与后台执行

- 迁移：`tailor_run`、`tailored_bullet` 表。
- LangGraph 图按 [02 第 3 节](./02-技术架构与数据模型.md#3-改写流程图v1-核心)：load_inputs → match → plan → rewrite → ground_check → revise / fallback → finalize。
- 检查点：`AsyncPostgresSaver`。自己建连接或连接池时必须带 `autocommit=True` 和 `row_factory=dict_row`（官方说明，否则建表可能不生效、读取会报错）；首次使用调用 `setup()`。
- thread_id 用 `{user_id}:{run_id}`，恢复运行前校验归属。
- 后台执行：接口创建运行记录后，用进程内后台任务执行图，状态写数据库；执行入口集中在一个函数。
- 改写时每条只放入相关事实和对应 JD 要求（[02 第 11.3 节](./02-技术架构与数据模型.md#113-各场景的做法)）。

**验收：** 端到端测试（假模型）覆盖：全部通过、修订后通过、两次修订仍失败而回退、预算耗尽。

### T2.5 E3、E4、E5

- E3：10 份简历 × 5 份 JD 的要求覆盖标注，并抽 50 条请第二个人标注。
- E4：约 300 句构造数据（正常与六类编造），评测三种检查组合。
- E5：A～D 四个版本的端到端编造率、回退率、token 与耗时。

## 9. 调研中发现的注意事项

- DeepSeek 开启 JSON Output 时，prompt 中必须出现「json」字样并给出格式示例，且 `max_tokens` 要设够，否则输出可能被截断（官方说明）。
- 思考模式下 `temperature` 等参数不生效也不报错，容易误以为设置成功；网关要按用途明确设置思考开关。
- `langgraph-checkpoint-postgres` 的连接要求 `autocommit=True` 与 `row_factory=dict_row`，与 SQLAlchemy 的连接分开管理（两者都用 psycopg 3，但不共用连接）。
- Colima 在电脑重启后不会自动启动，启动脚本要先检查。
- `docker compose down -v` 会清空数据库，平时只用 `down`。
