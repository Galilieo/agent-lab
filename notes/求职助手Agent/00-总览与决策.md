# 00 总览与决策

日期：2026-11-16。状态：**设计完成，已冻结（2026-11-16）**，尚未实施。修改规则见 [README 设计冻结规则](./README.md#设计冻结规则)。

## 1. 决定

用户于 2026-11-16 确定：agent-lab 的求职项目改做**实习求职助手 Agent**，与心屿并列为简历上的两个项目。

- 心屿：C 端情绪记录与 AI 陪伴产品，展示完整业务产品与 Java / Python 服务协作；推进节奏较慢，按心屿自己的计划进行。
- agent-lab（本项目）：效率工具类 Agent 应用，展示 Agent 能力深度、可信输出和评测；**优先完成**。

> **范围调整（2026-11-16，同日稍后）：** 用户决定 V1 **暂不上线、不推广**，定位为个人学习项目、本人求职时自己使用，在本地运行。但**多用户能力照常预留并实现**：用户表、基础登录、按用户的数据隔离、删除账号，并有跨用户隔离测试。部署上线、招募用户、完整对外隐私政策移到以后，需要时再按本套文档中保留的方案执行。代价是简历上暂时不能写「真实用户」，亮点改由评测数据和本人实际使用记录支撑。

### 1.1 为什么选它

求职目标是 **Agent 应用开发实习岗**。选题时考虑过「必须落地」；范围调整后 V1 改为个人使用，但这个题目仍然保留了以后开放给他人的可能。

| 标准 | 本项目的情况 |
| --- | --- |
| 真实使用场景 | 用户本人正在找实习，可以用真实 JD 和自己的简历持续使用；以后需要时，身边同学就是潜在用户；不依赖企业数据 |
| 能否快速落地 | 不需要企业内部数据或复杂环境，V1 预计 5 周左右可用（2026-11-16 改为对话式后的估计，未实测，以里程碑执行情况为准） |
| Agent 能力覆盖 | 结构化输出、工作流、工具调用、依据检查、记忆、RAG、多轮对话、多 Agent、MCP 都有自然的落脚点，见[第 4 节](#4-agent-能力与功能的对应) |
| 可讲的技术难点 | 改写不编造（依据检查）、长期记忆的更新与删除、面试追问策略、提示注入防御、评测设计 |
| 与心屿的关系 | 产品类型、用户场景、技术重点都不同，两个项目互补 |
| 面试共鸣 | 面试官容易理解；「我用它帮自己求职」是完整的故事 |

### 1.2 已知缺点

- **同类项目多。** 「AI 改简历」很常见。差异要靠：依据检查与编造率评测、长期记忆和面试追问的设计深度；以后开放后再加上真实用户数据。具体同类项目的对照见 [ASu-skills 对照](./参考-ASu-skills对照.md)（2026-11-16）。
- **部分质量难以客观评分。** 改写后「更适合这个岗位」带主观成分。对策是把能客观评的部分（编造率、JD 提取准确率、要求覆盖判断）做扎实，主观部分用盲评并说明样本量。
- **简历包含个人信息。** 个人使用阶段只涉及本人数据；以后开放给他人前，必须处理认证、隐私说明、数据删除，见 [03](./03-可信安全与隐私.md)。
- **暂时没有真实用户数据。** 个人使用阶段，简历上只能写评测结果和本人使用记录。

### 1.4 2026-11-16 修订：改为对话式 Agent

**原因：** 用户看过第一版原型（多页面、表单式）后，发现交互方式与设想不符：希望像通用 Agent 一样，通过对话提供资料、让 Agent 比对和生成简历、继续修改。另外，求职目标是 Agent 应用开发岗，面试最看重的正是会调用工具、带记忆、能管理上下文的对话式 Agent；原设计的工具调用和记忆都偏弱。

**改了什么：**

- V1 入口改为**对话 Agent**（01 F0）：左边对话，右边产物面板；工具分读取、生成、写入三类，**写入必须用户确认**。
- 原有的事实库、JD 解析、匹配、改写与三层依据检查**全部保留**，改为 Agent 调用的工具；依据检查在工具内部强制执行，Agent 绕不过去。
- 新增**岗位库**（F10）；对话与岗位**软绑定**。
- **轻量长期记忆**（求职偏好、写作偏好）、**短期记忆与上下文管理**、**流式输出**提前到 V1。
- V2 加入**岗位搜索**（F11），模拟面试改为对话的一种模式。
- 前端加 Ant Design X；参考 Open Canvas、Resume-Matcher、ASu-skills 的设计（02 决定 25）。

**不变的：** 核心卖点仍是「改简历不编造」以及用评测证明它；技术栈、数据库、登录与隔离方案不变；已完成的 T0.1～T0.5 不受影响。

**代价：** V1 从约 4 周变为约 5 周（05 第 2 节）。设计选型过程（四种布局、五种视觉风格）的结论见 [07 第 1 节](./07-前端界面规范.md#1-已确认的选择)。

### 1.5 为什么不用通用 Agent（2026-11-16）

这是 V1 改为对话式后必须回答的问题：ChatGPT、Claude 也能对话、有跨会话记忆、能读简历文件。调研了 Aider、xerj、Mem0、Open Canvas 等项目的做法（[参考-优秀项目的差异化设计](./参考-优秀项目的差异化设计.md)）后，JobPilot 的回答是：

| | 通用 Agent | JobPilot |
| --- | --- | --- |
| 经历从哪来 | 模型自己总结的记忆或上传的文件，用没用、怎么用看不到 | 用户逐条确认的**结构化事实库**：职责程度、来源、原文片段、版本 |
| 会不会编造 | 只能靠提示词要求「别编造」 | **可追溯改写**：每句必须引用事实编号，程序检查数字、技术名、职责程度，不符就修订，仍失败时采用本次已确认事实文字，无有效事实则标为待处理 |
| 怎么证明 | 无 | **公开的编造率基准**（04 E5）：同一批合成数据上，比较只靠提示词的通用模型与 JobPilot |
| 不确定时 | 倾向于给出一个答案 | **不确定就问**：原文对不上、说法矛盾、缺少关键信息时，用确认卡片问用户 |
| 多岗位管理 | 对话记录 | 岗位库、每份简历对应的岗位与事实库版本、可撤销的改动 |
| 跟通用 Agent 的关系 | — | 不竞争：V2 提供 MCP 服务，通用 Agent 可以直接调用事实库与带依据检查的改写 |

**诚实的边界：** 只改一份简历、不在乎细节的人，用通用 Agent 更方便。JobPilot 的价值在**多次使用**（很多岗位、很多版本）和**需要可信**（不能编造）的场景。README 要写明这一点。

**面试时的回答（约 30 秒）：** 通用 Agent 也有记忆，但它的记忆是模型自己总结的文字，改简历时用没用、有没有添油加醋看不到。我把经历做成用户确认过的结构化事实库，每句改写必须引用事实编号，再用程序检查数字和职责程度；拿不准就问用户。我公开了编造率基准：只靠提示词约束，编造率是 X%，加上程序检查后是 Y%（数字等 E5 跑完再填，不能估算）。另外我把它做成了 MCP 服务，通用 Agent 也能调用，两者不是竞争关系。

## 2. 目标用户与场景

**V1 使用者：** 用户本人。设计面向的人群是正在找 **技术类实习**（AI 应用、后端、前端、算法等）的在校生。先收窄到技术类，原因是：面经知识库和评测集更容易建，用户本人也最熟悉这类岗位。

**代表场景：**

> 我是大三学生，想投某公司的「AI Agent 开发实习生」。我把简历和 JD 截图丢进对话，Agent 告诉我这份 JD 的硬性要求和加分项，我的简历覆盖了哪些、缺了哪些，还提醒我「你做过 LangGraph 但简历没写」。我补充了一句到岗时间，它问我要不要加进事实库，我点了确认。然后它生成一份针对这个岗位调整过的简历，显示在右边，每一条都能回溯到我的原始经历；没有依据的内容会被拦下或标出。我在对话里说「语气别太浮夸」，它问要不要记住这个偏好，下次新开对话也会照做。（V2）面试前，我可以在同一段对话里开始模拟面试。

**不服务的场景（V1）：** 非技术岗位、海外求职、自动投递、代写求职信以外的长文写作。

### 3.0 V1 最小闭环（P0）与可延后（P1）

2026-11-16：V1 先保证最小闭环，其余迭代加入。P0 全部完成后再做 P1；时间不够的 P1 推到 V1.1，不影响 V1 完成。

| 功能 | P0：V1 必须 | P1：时间不够就放到 V1.1 |
| --- | --- | --- |
| 对话 Agent | 多段对话、流式输出、四类工具、写入确认、当前岗位软绑定、不确定就问、上下文只放最近 N 轮 | 撤销；早期轮次压缩成摘要（`conversation.summary`） |
| 经历事实库 | 多种格式解析、单张图片 OCR、事实拆分、职责程度、原文校验、确认与版本 | 多张截图自动排序去重、矛盾规则 |
| 岗位库 | JD 解析、基本字段、列表与详情、字段可修改 | 薪资换算与筛选、自定义字段、标签数量统计 |
| 匹配与改写 | 匹配报告（含表达缺口）、改写流程、三层依据检查 | — |
| 简历 | 完整简历、面板内编辑、依据追溯、导出 HTML 与 PDF（浏览器打印） | 自动一页、字体切换、DOCX 与 Markdown 导出、版本过期提示 |
| 记忆 | 偏好记忆：确认写入、查看、删除 | 删除后防重建 |
| 投递追踪 | — | 记录投递与简历快照、与现在对比 |
| 页面 | 对话页与右侧面板、岗位库、我的（经历、简历、记忆） | 工作台首页（先用岗位库代替） |
| 账号 | 登录、用户隔离、两阶段删除账号 | 导出全部数据 |
| 评测 | E1、E2、E4、E5（含公开基准）、E12 | E3 的第二人标注、E6、E11 |

### 3.1 V1 完成标准

- 功能：第 3.0 节的 **P0 全部完成**，能在本地通过网页使用；P1 不作为完成条件。
- 本人使用：用真实 JD 和自己的简历，**通过对话**走完至少 10 次「给 JD → 拿到定制简历」的完整流程，记录遇到的问题和改进（数字是目标，不是预测）。
- 运行：一条命令能在本地启动（README 写明步骤），别人克隆仓库后也能跑起来看演示。
- 多用户预留：注册登录、数据按用户隔离、删除账号可用；跨用户隔离测试（用户 A 无法通过任何接口读、改、删用户 B 的数据）全部通过。
- 评测：JD 解析集、依据检查集各有第一版结果；至少一组对照实验（有无依据检查的编造率）；E12 Agent 工具调用有第一版结果；写入未经确认不会生效的测试全部通过。
- 文档：README 写清功能、架构、评测结果和局限；有一段演示视频。

### 3.2 不算完成的情况

- 只能在命令行运行，没有可用的网页界面；或者别人按 README 无法跑起来。
- 只有单元测试通过，没有评测数据。
- 评测只有总分，没有说明样本量、标注方式和失败案例。

## 4. Agent 能力与功能的对应

每项能力都要回答「为什么这里需要它」，并有对照数据证明作用。标为「深做」的是面试主讲的亮点。

| 能力 | 用在哪里 | 为什么需要 | 阶段 | 深度 |
| --- | --- | --- | --- | --- |
| 结构化输出 | 简历拆成经历事实、JD 拆成要求清单 | 后续匹配和检查都依赖结构化数据 | V1 | 能用 |
| 工作流 / 规划 | 改写流程：匹配 → 规划 → 改写 → 依据检查 → 有限次修订 | 一步生成无法保证质量和依据 | V1 | 能用 |
| 依据检查（可信输出） | 改写后每条内容回溯到事实库 | 防止编造经历，这是产品的底线 | V1 | **深做** |
| 工具调用与人工确认 | 对话 Agent 调用解析、匹配、改写、导出等工具；写入类工具先暂停等用户确认 | V1 的主要交互方式；写入确认保证编造内容进不了事实库 | V1 | **深做**（E12） |
| 长期记忆 | V1：求职偏好、写作偏好；V2：弱项 | 对话式之后会开很多段对话，偏好要跨会话延续 | V1～V2 | **深做** |
| RAG | 面经与八股知识库、岗位库检索 | 出题和建议要基于真实资料，而非模型想象 | V2 | 能用，做检索评测 |
| 短期记忆与上下文管理 | 长对话只放最近 N 轮（P0），早期轮次压缩成摘要（P1）；改写时按条组装上下文；模拟面试的追问与历史摘要 | 控制成本、减少张冠李戴 | V1 | 能用，加一组对照（E11）；见 [02 第 11 节](./02-技术架构与数据模型.md#11-记忆与上下文管理) |
| 流式输出 | 对话回复、工具步骤、确认请求 | 降低等待感，让用户看到 Agent 在做什么 | V1 | 能用（复用 SSE） |
| 多 Agent | 面试官与评分分开；与单 Agent 对照 | 提问和评价是不同职责，需要验证拆分是否值得 | V3 | 对照实验 |
| MCP | 把求职工具包装成 MCP 服务 | 让其他客户端能调用 | V3 | 能用 |
| 提示注入防御 | 用户粘贴的 JD 文本可能含恶意指令 | JD 来自网络，属于不可信数据 | V1 基础，V3 专项评测 | V3 深做 |
| 可观测性与成本 | 记录每次运行的步骤、耗时、token | 长期使用要控制花费、定位问题 | V1 | 能用（复用模型调用记录） |
| 评测体系 | 全部功能 | 证明每项设计有效 | V1 起持续 | **深做** |

## 5. 非目标

- 不自动在招聘平台上投递，不批量抓取招聘平台数据。违反平台规则，也有法律风险。V1 的 JD 由用户自己提供；V2 的岗位搜索只用公开搜索结果或用户给的链接。
- 不保证「用了就能拿 offer」，产品文案也不做这类承诺。
- 不代替用户做职业规划决策，只提供依据和建议。
- V1 不做移动端 App。网页做好移动端适配即可。
