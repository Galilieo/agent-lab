# 参考：ASu-skills 对照

日期：2026-11-16。状态：参考资料，**不改变已冻结的设计**；文中「可借鉴」各项是否采用，按[设计冻结规则](./README.md#设计冻结规则)由用户决定后再写进 01～04。

## 1. 它是什么

[ASu-skills](https://github.com/Hisn00w/ASu-skills)（MIT 协议，阅读版本 `d27fd2a`）是一套中文求职插件，给 Claude Code、Codex 等 AI 编程助手使用。它由 9 个 Agent Skill 组成，每个技能是一个 `SKILL.md`：开头的 `name` 和 `description` 告诉助手什么时候调用，正文写工作流程和规则，较长的细则放在 `references/` 里，需要时才读。

本次阅读了 README 以及 `job-match`、`great-resume`、`interview` 三个技能和主张—证据账本模板。

## 2. 与 JobPilot 的对应

| ASu-skills | JobPilot | 说明 |

| `/job-match` 岗位匹配 | F3 匹配报告 | 都逐条对照 JD 要求，**都不给百分比匹配分** |
| `/great-resume` 简历提升 | F4 定制改写与依据检查 | 都禁止编造，缺信息时标记待补 |
| `/make-resume` 简历制作 | F5 导出 | 它有 18 个 HTML 模板；我们 V1 只导出 Markdown 和 DOCX |
| `/interview` 面试 | F6 模拟面试（V2） | 都是一次一问、按回答追问 |
| `/offer` 进度管理 | F9 投递追踪（V2） | |

## 3. 根本区别（面试时会被问「和已有项目有什么不同」）

| | ASu-skills | JobPilot |
| --- | --- | --- |
| 形态 | 写给通用 AI 助手的提示词包，运行在用户的编程助手里 | 独立的 Web 应用：数据库、登录、多用户隔离、后台任务 |
| 防编造靠什么 | **自然语言规则**：在 `SKILL.md` 里写明“不添加用户没做过的技能”，由模型自觉遵守 | **程序强制**：改写必须引用已确认的事实 ID；第一、二层由代码比对数字、技术名、角色词；第三层再由模型检查；不通过就修订或回退 |
| 效果怎么证明 | 没有评测数据 | E5 对照实验测编造率，一次只改一个变量 |
| 数据保存 | 对话上下文加本地文件 | PostgreSQL，事实库有版本，改写结果可追溯到用于生成它的事实库版本 |

一句话概括：**ASu-skills 用提示词约束模型，JobPilot 用程序校验约束模型，并用评测量化效果。** 两者并不互斥，好的提示词规则可以直接用在我们的 prompt 里。

## 4. 可借鉴的地方

### 4.1 匹配状态分得更细（对应 F3，T2.1）

我们的判断只有「已覆盖、部分覆盖、未覆盖」三种。它分五种：

| 状态 | 含义 |
| --- | --- |
| 已匹配 | 有明确证据 |
| 表达缺口 | 做过，但简历没写清楚 |
| 证据不足 | 材料暗示可能具备，但不足以对外写 |
| 真实缺口 | 确实不具备 |
| 待确认 | 缺少决定性信息 |

其中**「表达缺口」对我们特别有价值，而且可以由程序判断**：事实库里有这条事实（例如用户手动补充的），但当前简历原文里没有体现。这正是定制改写最该做的事。另外它把硬性门槛（学历、地点、年限等）单独列出，不被其他优势抵消；结论用「建议投递 / 补充材料后投递 / 谨慎投递 / 暂不建议投递」四档。

### 4.2 事实记录个人职责边界（对应 F1，T1.4）

它的账本每条主张都有 `responsibility_level`（负责模块、参与等）和 `boundary`（个人边界，例如“只负责文档，不涉及核心代码”）。我们的事实类型里有「角色」，但没有单独的职责程度字段。依据检查第二层要比对「主导」「负责」这类角色词，如果事实本身带职责程度，检查规则会更简单、更可靠。

### 4.3 改写的写法（对应 F4 的 prompt，T2.4）

- 改写结构：「动作 → 系统能力 → 业务价值 → 结果证据 → 个人边界」。
- 缺信息时输出 `【待补】` 占位，而不是空着或编一个。
- 强动词规则：只有能说明决策、交付和结果时，才用「主导」「负责人」。

这些只影响 prompt 文件，不改变设计，写 prompt 时可以直接参考。

注意：它也有偏“包装”的规则，例如把 typo、README 修复总结为“跨项目文档质量治理”。这类拔高表述与我们的立场不一致，不借鉴。

### 4.4 模拟面试（对应 F6，V2）

- **按主张类型追问**：Ownership（个人范围）、Metric（指标口径、分母、基线）、Technical（在项目里的具体作用）、Architecture（数据流、边界、故障处理）、Result（是否真实交付）。可以直接作为我们出题规划的考察点分类。
- **停止条件写清楚**：证据充分最多再追一个反事实问题；连续两次没有新信息就停止该分支；预算用完就收尾。
- **复盘不打精确总分**：按「已验证、部分验证、未验证、矛盾」归类。我们 F6 原设计是逐题按维度评分，E10 再做校准，可以对照考虑。
- **弱项复练用变体题**，不原题重问；这与我们 F8 记录弱项的长期记忆可以结合。

### 4.5 评测上的一个对照点（对应 E5）

E5 的基线 A 是“直接让模型改写”。可以考虑加一个 A'：**A 加上写进提示词的事实边界规则**，也就是 ASu-skills 这类做法。如果 C、D 的编造率明显低于 A'，就能用数据说明“程序检查比只靠提示词约束更可靠”。这是面试时很有说服力的一张表。

### 4.6 Agent Skills 机制本身

它是学习 Agent Skills 的好例子：

- `description` 决定何时被调用，相当于路由；
- 正文只写流程和规则，细则放在 `references/`，需要时再读，这叫**渐进式加载**，目的是节省上下文；
- 技能之间通过「交接」配合（例如 `/job-match` 把表达缺口交给 `/great-resume`）。

这和我们 02 第 11 节的上下文拼装是同一类问题：哪些内容常驻上下文，哪些按需加载。JobPilot 的主流程是固定的 LangGraph 工作流，不需要技能机制；如果以后做开放式对话（例如 V3 的求职问答），可以再考虑。

## 5. 自己求职时直接用

它本身就能帮你求职，可以在 Claude Code 里安装：

```text
/plugin marketplace add Hisn00w/ASu-skills
/plugin install asu-skills@asu
```

比较适合现在用的是 `/interview grill`（拿自己的简历练被追问）和 `/job-match`。使用时注意：

- 简历内容会发给对应的模型服务，和使用任何 AI 工具一样；
- `/job-apply` 会操作浏览器填写网页，它默认停在提交前，最终提交仍要自己确认；
- 用它产生的结论（例如面试复盘）是你自己的练习材料，不能当成 JobPilot 的评测数据。
