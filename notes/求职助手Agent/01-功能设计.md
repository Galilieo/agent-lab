# 01 功能设计

日期：2026-11-16。状态：设计方案，尚未实施。限额数字是起点，使用中按数据调整。

> **2026-11-16 修订（对话式）：** V1 的入口改为对话 Agent（新增 F0），岗位库成为独立功能（新增 F10），长期记忆的偏好部分提前到 V1（F8），岗位搜索列为 V2（新增 F11）。F1～F5 的规则不变，改为由 Agent 调用的工具完成，结果显示在对话右侧的面板里。界面见 [07](./07-前端界面规范.md) 与[原型](./prototype/index.html)。

## 总流程

```text
                        对话 Agent（F0）：用户说话、丢简历 / JD / 截图
                                         │ 调用工具
      ┌──────────────┬───────────────────┼──────────────────┬──────────────────┐
      ▼              ▼                   ▼                  ▼                  ▼
 经历事实库（F1）  JD 解析（F2）       匹配报告（F3）    改写 + 依据检查（F4）  长期记忆（F8）
 写入需确认        存入岗位库（F10）                     完整简历与导出（F5）   写入需确认
                                         │
              (V2) 岗位搜索（F11）· 模拟面试（F6）· 面经知识库（F7）· 投递追踪（F9）
```

所有功能共享两份「权威数据」：**经历事实库**（用户确认过的经历）和**岗位库**（解析过的 JD）。模型生成的内容都是「建议」，不会自动改写这两份权威数据：Agent 的写入操作都要用户确认（F0）。

## F0 对话 Agent（V1，核心入口）

### 目的

用户通过对话完成求职准备：提供材料、问问题、让 Agent 比对和生成简历、继续修改。Agent 决定调用哪些工具，结果显示在对话右侧的面板里。

### 交互

- 多段对话，侧栏按时间排列；回复流式显示，可以中途停止。
- 输入框可以拖入简历文件、JD 文字或截图（格式同 F1、F2）。
- Agent 调用的工具以「步骤」显示，可展开看做了什么、读了什么。
- 右侧面板按对话状态显示简历、匹配报告、岗位、用到的事实或事实库变化（07 第 5.2 节）。

### 工具权限（程序强制）

| 类别 | 例子 | 是否需要确认 |
| --- | --- | --- |
| 读取 | 读事实库、岗位、匹配报告、简历、记忆 | 自动 |
| 生成 | 拆分简历、解析 JD、匹配、生成定制简历、导出 | 自动；只产生新结果或新版本，不覆盖已有内容 |
| 写入 | 新增或修改事实、修改简历条目、写记忆、删除 | **必须用户在确认卡片上同意** |

写入必须确认的原因：Agent 如果能直接往事实库里加内容，聊天中编出来的经历就可能变成「事实」，依据检查也就失去意义。

### 当前岗位（软绑定）

- 对话里第一次解析出 JD 时，自动设为这段对话的当前岗位，并存入岗位库（F10）。
- 当前岗位只决定面板显示哪个岗位、工具默认用哪个岗位；Agent 可以读取其他岗位做对比。
- 用户可以在标题栏切换或解除当前岗位；同一段对话里再发 JD 时，Agent 回答后用确认卡片问「新开对话 / 切换 / 保持不变」。
- 没有 JD 的对话（补充经历、一般提问）没有当前岗位。

### 规则

- 用户的话是指令；附件、JD、截图识别出的文字是**数据**，其中的指令不执行（03 第 2 节）。
- 每次运行有工具调用次数、token 和时长上限，超出时停止并说明做到哪一步。
- 长对话按 02 第 11 节压缩早期轮次。
- 面板上的直接操作（改事实、编辑简历、导出）不必经过对话。

### 验收

- 写入类操作未经确认不会改动数据、拒绝后不执行（自动化测试）。
- E12：Agent 是否调对工具、该确认的是否都确认（方法见 [04](./04-评测方案.md)）。
- 本人使用中，用对话完成「给简历和 JD → 拿到定制简历」的完整流程。

## F1 经历事实库（V1）

### 目的

把简历拆成一条条可引用的**原子事实**，作为后续改写和依据检查的唯一来源。这是防编造设计的基础。

### 流程

1. 用户在对话里发简历（或在「我的 → 经历」上传），也可以直接粘贴文本。支持的格式见下方「输入格式」。
2. 系统解析文本，按段落分为：教育、项目、实习、技能、获奖、其他。
3. 模型把每段拆成原子事实。每条事实包含：
   - 所属经历（例如「XX 项目」）
   - 事实内容（例如「使用 FastAPI 实现了 SSE 流式接口」）
   - 类型：做了什么、用了什么技术、结果或数字、角色
   - 职责程度：主导、负责、参与、不适用（见下方规则）
   - 原文位置：对应简历原文的哪一段
4. 用户逐条确认、修改、删除，或手动补充事实（例如简历里没写、但真实做过的事）。
5. **只有用户确认过的事实**，才能被改写引用。

### 规则

- 数字类事实（「提升 30%」「日活 500」）单独标记类型，后续依据检查对数字做严格比对。
- 用户手动补充的事实标记来源为「用户补充」，与「简历解析」区分。
- 事实库有版本号；改写结果记录基于哪个版本生成。
- **原文校验**（2026-11-16，参考 xerj）：来自简历的事实保存原文片段（`source_quote`）与位置，程序校验片段确实是简历原文的那一段（去掉空白后比较）。对不上的事实不能直接确认，按下方「不确定就问」处理。
- **职责程度**（2026-11-16 加入 V1，参考 [ASu-skills 对照](./参考-ASu-skills对照.md)第 4.2 节）：项目与实习中的事实标记为主导、负责、参与之一；教育、技能、获奖等标记为不适用。
  - 主导：做出关键决策并对整体交付负责；负责：独立负责其中一个模块或一部分工作；参与：参与或协助。
  - 模型按简历原文的措辞给出初判；原文没有明确说法时默认「参与」，并在确认界面提示用户核对。
  - 依据检查第二层用它判断改写中的角色词是否越级，见 [03 第 1.2 节](./03-可信安全与隐私.md#12-三层检查)。

### 不确定就问（2026-11-16）

拿不准时不猜，用确认卡片问用户（F0 的确认机制），问完再写入：

| 情况 | 怎么发现 | 问什么 |
| --- | --- | --- |
| 原文对不上 | 原文校验失败 | 「这条是这个意思吗？」可以修改或确认 |
| 说法矛盾 | V1：程序规则比较同一类字段（成绩、日期、同一段经历的数字）；V2：模型检查语义矛盾 | 列出几种说法，让用户选一个或自己填 |
| 职责程度不明 | 原文没有明确说法 | 参与 / 负责 / 主导 |
| 缺少关键信息 | 当前岗位的硬性要求需要、事实库里没有（例如到岗天数） | 直接问，用户回答后提议加进事实库 |

问题合并：一轮回复最多一张提问卡片，几个问题放在一起问，不要聊一句打断一次。用户可以选「先跳过」，跳过的事实不能被改写引用。

### 边界情况

| 情况 | 处理 |
| --- | --- |
| PDF 是扫描图片，提取不到文字 | 自动转为图片做文字识别（OCR），识别结果先给用户核对 |
| 旧版 Word（.doc）、Pages 等格式 | 提示另存为 DOCX 或 PDF 后再上传 |
| 解析出的事实与原文不符 | 用户在确认环节修改；记录修改次数，作为解析质量的使用指标 |
| 简历很长（超过 3 页） | 正常处理，但提示技术实习简历一般建议控制在 1 页 |

### 输入格式（2026-11-16 扩充）

| 格式 | 处理方式 |
| --- | --- |
| PDF（文字版） | 直接提取文字 |
| PDF（扫描版）、图片（PNG、JPG、WebP） | 本地 OCR 识别文字，**识别结果先显示给用户核对修改**，再拆分事实 |
| DOCX | 直接提取文字 |
| TXT、Markdown、HTML | 直接读取文字（HTML 去掉标签），方便把本项目导出的 HTML 简历再导回来 |
| 粘贴文本 | 直接使用 |

OCR 在本机运行（见 [02 决定 20](./02-技术架构与数据模型.md#91-以后很难改已经定下的)），图片不发送给模型供应商。上传的原文件解析后都不保存。

#### 多张截图的整理（简历与 JD 共用，2026-11-16）

用户可能乱序上传，长页面截图之间通常还有重叠。处理分三步：

1. **逐张识别**：每张图片单独在本地 OCR，得到各自的文字。
2. **模型只决定顺序**：把各张的识别文字（不是图片）作为数据交给模型，模型按内容的连贯性输出顺序，例如 `[3, 1, 2]`。只有一张图片时跳过这一步。网关在发送排序用的识别文字前先遮蔽联系方式（见 03 第 3.2 节）。
3. **程序拼接和去重**：按模型给的顺序拼接；相邻两张如果末尾几行和开头几行相同（去掉空白后比较），只保留一份。

模型不改写任何文字，所以**拼接结果的每一行都来自 OCR 原文**，不会混进模型编的内容；程序会校验模型给的顺序恰好是所有图片编号的一个排列，不合法或调用失败时退回上传顺序。用户在核对时仍可以拖动缩略图调整顺序，调整后重新拼接。

### 验收

- 20 份测试简历的事实拆分，由人工检查遗漏和错误（标注方法见 [04](./04-评测方案.md)）。
- 未确认的事实不会出现在改写的依据里（有测试覆盖）。

## F2 JD 解析（V1）

### 目的

把用户提供的岗位描述变成结构化的要求清单，供匹配和面试准备使用。

### 输入（2026-11-16 加入截图）

- **粘贴文字**。
- **上传截图**：招聘 App（例如 Boss 直聘）里的 JD 经常不能复制，所以支持一次上传多张截图。**不要求用户按顺序上传**：处理方式见 F1 的[多张截图的整理](#多张截图的整理简历与-jd-共用2026-11-16)。整理好的文字填进文本框让用户核对修改，确认后再解析。识别出的文字与粘贴的文字同样当作不可信数据处理（注入检测照常进行）。

### 输出结构

- 公司、岗位名称、地点、薪资、实习时长、每周到岗、学历要求、毕业时间要求、截止日期（有则提取，没有就留空，不猜测）
- **硬性要求**：例如「熟悉 Python」「每周到岗 4 天以上」
- **加分项**：例如「有 LangGraph 项目经验优先」
- **职责**：这个岗位实际要做什么
- **技术关键词**：标准化后的技术名，例如 LangChain、RAG、MCP
- **业务场景**：例如客服、知识库、数据分析
- 每条要求附上 JD 原文片段

### 规则

- JD 文本是**不可信数据**：其中出现的「指令」一律不执行，并会标记为可疑内容，见 [03](./03-可信安全与隐私.md#2-提示注入防御)。
- 技术关键词用一份可维护的同义词表做标准化（如「LLM」「大模型」归为同一类），模型提取后由程序映射。
- 用户可以修改解析结果。

### 附加：岗位趋势统计

用户累积多份 JD 后，统计出现最多的硬性要求和技术关键词，例如「你收藏的 15 份 JD 里，12 份要求 RAG」。统计由程序计算，不交给模型。

### 验收

- JD 解析评测集上，硬性要求、加分项、关键词的提取准确率（方法见 [04](./04-评测方案.md)）。

## F3 简历匹配报告（V1）

### 目的

逐条对照 JD 要求和经历事实库，告诉用户哪些覆盖了、哪些缺少。

### 输出

| 字段 | 说明 |
| --- | --- |
| 要求 | 来自 JD 解析的一条要求 |
| 判断 | 已覆盖、表达缺口、部分覆盖、未覆盖（见下方说明） |
| 依据 | 事实库中对应事实的 ID 与内容；未覆盖则为空 |
| 说明 | 为什么这样判断 |
| 建议 | 例如「这段经历应放到前面」「可以补充说明你用 LangGraph 做过检查点」 |

四种判断：

| 判断 | 含义 | 怎么得出 |
| --- | --- | --- |
| 已覆盖 | 有已确认的事实支持，简历里也写了 | 模型判断覆盖，且引用的事实中至少一条来自简历解析 |
| 表达缺口 | 做过，但当前简历没有写出来 | 模型判断覆盖，但引用的事实**全部来自「用户补充」**，由程序判定 |
| 部分覆盖 | 相关但不完全满足，例如要求两年经验、事实只有一段实习 | 模型判断 |
| 未覆盖 | 事实库中没有相关事实 | 模型判断 |

「表达缺口」（2026-11-16 加入 V1，参考 [ASu-skills 对照](./参考-ASu-skills对照.md)第 4.1 节）是定制改写最该补的内容：不需要新增经历，只需要把已确认的事实写进简历。

另外给出整体概况：硬性要求单独列出覆盖情况，不被其他优势抵消；主要短板是什么。**不给一个笼统的「匹配度 87%」分数**，因为这种分数没有可靠的含义，容易误导用户。

### 规则

- 「已覆盖」「表达缺口」「部分覆盖」必须引用至少一条事实；引用的事实 ID 由程序校验确实存在且已确认。
- 对于缺少的技能，建议只能是「学习 / 补项目」或「如果你真的做过，请补充到事实库」，**不能建议用户直接写上去**。

### 验收

- 匹配判断评测集上，人工标注与系统判断的一致率。

## F4 定制改写与依据检查（V1，核心亮点）

### 目的

针对一个 JD 生成一份调整过的简历，每一条内容都能回溯到用户确认过的事实。

### 允许与禁止

| 允许 | 禁止 |
| --- | --- |
| 调整措辞，使用 JD 中的术语（前提是事实支持） | 加入事实库里没有的经历、技术、职责 |
| 调整经历和条目的顺序 | 编造或放大数字（例如把「参与」改成「主导」，把 30% 改成 50%） |
| 合并、拆分、删减条目 | 把「了解」升级成「精通」 |
| 突出与 JD 相关的事实 | 改动教育背景、时间、公司名等基本信息 |

### 流程

```text
匹配报告
  │
  ▼
改写规划：决定保留哪些经历、顺序、每条要突出什么（输出结构化计划）；优先把「表达缺口」对应的事实写进简历
  │
  ▼
逐条改写：每条输出 = 文本 + 引用的事实 ID 列表
  │
  ▼
依据检查（见 03）
  ├── 全部通过 ──▶ 生成最终版本
  └── 有问题 ──▶ 带着问题清单修订（最多 2 次）
                   └── 仍未通过 ──▶ 回退到本次事实库中已确认的事实文字；无有效事实则标「待处理」
```

### 依据检查的三层

1. **结构检查（程序）：** 每条内容必须引用至少一条已确认的事实 ID。
2. **数字与实体检查（程序）：** 改写文本里出现的数字、公司名、技术名，必须在引用的事实中出现过，或在允许的同义词表内；角色词（主导、负责、参与）的等级不能高于引用事实的职责程度。
3. **语义支持检查（模型）：** 由一个独立的检查调用判断「引用的事实是否支持这句话」，输出支持、部分支持、不支持，并说明理由。

详细设计见 [03 第 1 节](./03-可信安全与隐私.md#1-防编造依据检查)。

### 用户界面

- 改写过程在对话里以步骤显示；完成后直接生成完整简历（F5），显示在右侧面板。（2026-11-16 修订：原为逐条审阅页面）
- 简历中每条改写悬停可看检查结果与依据事实；被回退的条目注明原因。
- 用户可以在面板里直接修改，也可以在对话里说「把这条写得更偏工程」，Agent 提出修改并经用户确认。两种修改都要过一次依据检查，结果只做提示，不阻止保存。
- **改动可撤销**（2026-11-16，参考 Aider 的 `/undo`）：Agent 每次经确认的写入（新增或修改事实、修改简历条目、写记忆）都记录在 `agent_action`，对话里和面板上提供「撤销上一次改动」。事实库通过版本回退，简历保留旧版本。

### 验收

- 依据检查评测集上的检测准确率，以及端到端的编造率（方法见 [04](./04-评测方案.md)）。
- 对照实验：有依据检查与没有依据检查的编造率差异。

## F5 完整简历预览、编辑与导出（V1）

2026-11-16 修订：原为「导出 Markdown 与 DOCX」，现改为先生成一份完整简历、可二次编辑，再导出。

### 生成完整简历

改写运行完成后，自动组装一份**完整的定制简历**，不只是改写过的条目：

- 改写启动前默认选本人最近上传的简历，用户可以手动更换。启动后固定这份底稿，结构沿用底稿的分段（教育、项目、实习、技能等），顺序按改写规划调整。
- 用户选择接受时采用改写文字；选择不用或检查失败需要回退时，只取本次运行 `fact_set` 中对应的已确认事实文字；没有有效事实就标为「待处理」，不自动放回上传简历的原句。未改写的基本信息、教育等从固定底稿原样保留。
- 规划中补入的「表达缺口」条目放到对应经历下。
- 版式（V1 一套）：单栏 A4；顶部姓名、求职意向、联系方式、到岗信息（可立即到岗、每周天数、可实习时长）；各段标题带细分隔线；经历行左侧名称、右侧时间，下一行灰色技术栈；条目写成「加粗短标题：具体内容」。

### 预览与二次编辑

参照 ASu-skills 的可编辑 HTML 简历（见 [对照文档](./参考-ASu-skills对照.md)第 4.7 节）：简历按 A4 版式显示，点击文字直接修改，上方一条工具栏。**同一份编辑器既嵌在应用的预览页里，也随导出的 HTML 文件一起带走**，离线打开导出文件也能继续编辑。

编辑规则：

- 修改基本信息、教育等未经改写的部分不做依据检查。面板保存和 Agent 修改卡都携带开始编辑时的 `base_version_id`；版本冲突返回 409，保留用户草稿。
- 编辑结果单独保存，不会改动经历事实库；如果手动修改里出现了事实库没有的新内容，提示用户「如果属实，可以补充到事实库」。

## F6 模拟面试（V2）

### 目的

针对具体 JD 和用户的经历，做多轮模拟面试，并给出可执行的反馈。

### 流程

1. 用户在岗位对话里说「开始模拟面试」（作为对话的一种模式），选择面试类型：项目深挖、技术基础（八股）或混合。
2. **出题规划**：根据 JD 要求、事实库里的项目、面经知识库检索到的真实题目，生成本场的考察点清单（例如 6～8 个）。
3. **面试循环**：
   - 面试官提问 → 用户回答 → 判断要追问还是换题。
   - 追问策略：回答空泛时追问细节（「你具体负责哪部分？」「为什么选 X 而不是 Y？」），回答错误时追问原理，回答充分时进入下一个考察点。
   - 每个考察点最多追问 2 次，整场设轮数上限。
4. **结束后评估**：由独立的评分步骤，按评分标准（准确性、深度、表达清晰度、与经历是否一致）逐题评价，并**引用用户回答的原话**作为依据。
5. **写入弱项**：把反复出错的知识点作为候选记忆，**由用户确认后**才写入长期记忆。

### 规则

- 面试官不能引用事实库以外的经历来提问（例如不能问「你在 XX 公司实习时……」，除非事实库里有）。
- 八股题的参考答案来自知识库，并显示来源；知识库没有的题目，标注「参考答案由模型生成，可能有误」。
- 支持文字作答。语音作答延后，不在 V2 范围。

### 验收

- 评分与人工评分的一致性校准（方法见 [04](./04-评测方案.md)）。
- 追问是否针对用户回答的内容（人工抽检）。

## F7 面经知识库（V2）

- **来源：** 用户自己整理或获授权的面经和八股资料，以及用户在本产品中做过的面试记录。**不抓取**第三方平台的内容。
- **用途：** 模拟面试出题、八股参考答案、按岗位类型查高频题。

- 每条知识带来源和更新时间。

## F8 长期记忆（V1 偏好，V2 弱项）

2026-11-16 修订：偏好部分提前到 V1。对话式之后会开很多段对话，没有记忆每次都要从头讲。

### 记什么

| 类型 | 阶段 | 例子 | 写入方式 |
| --- | --- | --- | --- |
| 求职偏好 | V1 | 目标方向、城市、不投的岗位类型 | Agent 在对话中提议，用户确认后写入 |
| 写作偏好 | V1 | 语气平实、每条不超过两行、技术名用英文 | 同上 |
| 弱项 | V2 | 模拟面试里反复答不好的知识点 | 面试结束后提出候选，用户确认后写入 |

V1 每段对话把全部记忆放进上下文，不做检索；条数多了再在 V2 加按需选择。

### 与经历事实库的区别

- **经历事实库是权威数据**：简历内容只能来自这里。
- **记忆是辅助上下文**：用来个性化建议和出题，**不能作为改写简历的依据**。经历一律进事实库，不进记忆。
- 这条边界由程序强制：改写的内容只能来自事实库；写作偏好只影响措辞，其他记忆不进入改写。

### 规则

沿用 [Memory V1.1 方案](../Memory-V1.1轻量分层长期记忆方案.md)的分层、更新、删除和防重建设计。用户可以在「我的 → 记忆」查看、修改、删除所有记忆；删除后不会被 Agent 从旧对话里再提议回来。

### 验收

- 记忆评测场景：跨会话召回、改口后更新、删除后不再出现（方法见 [04](./04-评测方案.md)）。

## F9 投递追踪（V1 轻量版，V2 完整版）

2026-11-16 修订：轻量版提前到 V1，保存**记录投递时选定的版本**，方便面试前查看。离线编辑和外部发送由用户完成，系统只能追溯所选版本。

**V1 轻量版：**

- 在岗位详情或对话里标记「已投递」：投递日期（默认今天）、渠道、使用哪份简历（默认当前版本）。在对话中由 Agent 提议，属于写入操作，需要确认。
- **出卡时绑定版本**：保存所选的 `resume_version_id`。确认时从该版本冻结内容、事实库版本和 HTML；等待期间即使出现新版，也沿用卡片上的版本。同一张卡重复提交，按 `action_id` 返回原结果。
- 岗位上显示投递记录：时间、渠道、「查看记录投递时选定的版本」「下载 PDF」。
- 进度手动更新：已投递 → 笔试 → 面试 → offer / 未通过。首页看板与岗位库筛选都加上「已投递」。
- **与现在对比**：比较记录投递时选定的版本与当前版本：
  - 简历差异：按条目比较快照与当前版本，列出修改、新增、删除，前后并排；
  - 事实库差异：投递之后新增或修改了哪些经历（例如「投递后补充了压测经历，面试时可以主动提」）；
  - 风险提醒：快照里的某条表述后来因依据不足被回退或改弱时标出来，提醒面试时按当时的写法准备，但不要再往上夸大。
  - 对比由程序根据结构化的简历内容与事实库版本计算，不调用模型。

**V2 完整版：**

- 更细的阶段（一面、二面、HR 面等）。
- 面试后，用户粘贴或口述面试问题，Agent 整理成复盘：问了什么、答得怎样、要补什么。复盘中的题目可选择加入个人面经库。
- 统计：投递数、各阶段转化，由程序计算。
- 提醒：例如笔试截止时间（站内提醒，不接邮件或短信）。

## F10 岗位库（V1 个人，V2 共享）

- 对话中解析过的 JD 自动存入，也可以在岗位库直接添加（粘贴或截图）。
- 按方向、技术关键词、城市、进度筛选，标签旁显示数量；分类来自 F2 的关键词标准化，数量由程序统计。
- 每个岗位显示薪资、地点和匹配摘要（硬性要求覆盖、表达缺口）。
- **岗位详情**（2026-11-16）：基本信息字段包括公司、工作地点、薪资、每周到岗、实习时长、学历要求、毕业时间要求、截止日期、投递渠道、岗位链接；JD 没写的显示「未填写」，不猜测。**所有字段都可以修改或留空，也可以添加自定义字段**（例如内推人、面试轮数）。下面是岗位职责、硬性要求、加分项、技术关键词和 JD 原文。
- 薪资统一换算成「元/天」用于筛选，原始写法（例如「8k–10k/月」）保留显示。
- 详情页提供「回到这个岗位的对话」，没有对话的新开一段并设为当前岗位。
- 数据分两部分：**岗位本身**（JD 原文、解析结果）与**我和岗位的关系**（进度、匹配、简历、备注、用户修改过的字段与自定义字段）。后者永远私有；前者 V2 开放共享时，相同 JD 去重后对所有用户可见，不显示添加者（02 决定 23）。

## F11 岗位搜索（V2）

- 根据用户的求职偏好和事实库，搜索匹配的公开岗位信息，结果存入岗位库。
- 只使用公开的搜索结果或用户提供的链接，**不批量抓取招聘平台**，遵守平台规则。
- **搜索词里不能包含简历或事实库的内容**，防止外部内容中的恶意指令诱导 Agent 把用户信息发出去（03 第 2 节）。
