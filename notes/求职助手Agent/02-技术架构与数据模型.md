## 2. 整体架构

下图是以后开放给他人时的完整形态。V1 本地运行时没有 Caddy，其余结构相同；「认证与归属校验」一层在 V1 照常实现。

**用户隔离的实现原则：**
- user_id 只来自登录态，由依赖注入提供给路由，**不接受请求体或查询参数中的 user_id**。
- 数据访问函数的第一个参数都是 user_id，SQL 一律带 `WHERE user_id = ?`；按 ID 查单条记录时，ID 和 user_id 一起作为条件，查不到就返回 404（不区分「不存在」和「无权访问」，避免泄露其他用户的数据是否存在）。
- 关联数据（例如事实引用、岗位、改写运行）在使用前再校验一次归属。
- 向量表（V2）带 user_id 外键并级联删除，检索 SQL 同样带 user_id 条件；LangGraph 的 thread_id 带上 user_id 前缀，并在恢复运行前校验归属。

```text
浏览器（前端）
   │  HTTPS
   ▼
Caddy（HTTPS、静态文件）
   │
   ▼
FastAPI
 ├── 认证与归属校验：每个请求从登录态取 user_id，所有数据按 user_id 隔离
 ├── 业务接口：事实库、岗位、改写、面试、投递、记忆
 ├── 工作流层（LangGraph）
 │     ├── 改写流程图
 │     └── 模拟面试图（V2）
 ├── 能力层
 │     ├── 文件解析     ├── 依据检查     ├── 注入检测
 │     ├── 检索（V2）   ├── 记忆（V2）   └── 导出
 ├── 模型调用层：统一入口、重试、预算、调用记录
 └── 存储：PostgreSQL（业务数据 + checkpoint + pgvector 向量）
```

## 3. 改写流程图（V1 核心）

```text
START
  │
  ▼
load_inputs        读取已确认事实（指定版本）与 JD 解析结果；不读取长期记忆
  │
  ▼
match              生成匹配报告（若已有同版本报告则复用）
  │
  ▼
plan               生成改写计划：保留哪些经历、顺序、每条要突出的 JD 要求
  │
  ▼
rewrite            逐条改写，输出 {text, fact_ids}
  │
  ▼
ground_check       三层依据检查（03 第 1 节）
  │
  ├── 全部通过 ───────────────────────────────▶ finalize
  ├── 有问题且修订次数 < 2 ──▶ revise ──▶ ground_check
  └── 有问题且修订次数 = 2 ──▶ fallback（问题条目回退原文并标记） ──▶ finalize
  │
  ▼
finalize           保存版本，记录运行统计
END
```

### 3.1 状态（State）

| 字段 | 说明 |
| --- | --- |
| run_id | 本次运行 ID |
| user_id | 来自登录态，不由请求体传入 |
| fact_version | 使用的事实库版本 |
| job_id | 岗位 ID |
| match_report | 匹配报告 |
| plan | 改写计划 |
| bullets | 改写条目列表，每条 {bullet_id, text, fact_ids, check_status, issues} |
| revision_count | 修订次数 |
| budget | 剩余模型调用次数与 token |

### 3.2 预算

- 每次改写运行：模型调用次数上限、token 上限、总时间上限（具体数值先按开发集测出的中位数的 2～3 倍设定）。
- 超出预算：停止，保存已完成部分，告诉用户哪些条目没有完成。
- 每个用户每天的运行次数上限，防止滥用并控制成本。

### 3.3 恢复

- 每个节点结束写 checkpoint。服务重启后，未完成的运行可以从最后一个节点继续。
- 模型调用不保证恰好一次：重启后可能重新调用已发出但结果未知的请求。改写是纯生成，重复调用只影响成本，不影响数据正确性。

## 5. 数据模型

所有业务表（包括子表）都有 `user_id`，外键指向用户表并级联删除，所有查询都按 user_id 过滤。子表也冗余存 user_id，是为了让每条 SQL 都能直接带上隔离条件。时间统一用 `timestamptz`（按 UTC 存储）；结构化结果（如 parsed_json、items_json）用 JSONB。V2 的知识库切块表带 `embedding vector(维度)` 列，维度以所用 Embedding 模型为准。

### 5.3 数据删除

**账号（两阶段）：**
1. 申请删除：记录 `deletion_requested_at`，注销全部登录 session，停止该用户正在执行的运行。
2. 待删除期（7 天）：可以登录，但登录后只能选择「恢复账号」，其他接口一律拒绝。
3. 彻底删除：清理任务找出到期账号，通过外键级联删除全部业务数据和向量，再删除 checkpoint 中该用户的运行；`model_call` 与 `event` 的 user_id 外键设为 `ON DELETE SET NULL`，只保留匿名统计。每次清理记录删除数量。

**清理任务：** 不引入任务队列。后端启动时执行一次，之后在进程内每天执行一次；另提供一个手动执行的命令，方便测试。

**其他内容：** 岗位、改写结果、投递记录等直接删除（前端二次确认）。经历事实删除只影响新版本，旧版本与用它生成的改写结果保留。

**测试：** 待删除期间除恢复外的接口都被拒绝；彻底删除后任何接口都查不到该用户的数据；恢复后数据完整。

## 7. 模型调用网关

所有模型调用都通过 `llm_gateway`，统一处理：

1. **用途标签**：每次调用标明 purpose，便于按功能统计成本和失败率。
2. **预算**：检查当前运行与当前用户的剩余预算，不足则拒绝调用。
3. **重试**：只对超时、连接错误、上游 5xx 有限重试；结构化输出校验失败另计一次修复重试。
4. **记录**：写入 model_call 表，包括失败。
5. **不可信内容包装**：JD 原文、用户回答等不可信文本，统一放进明确的数据区块，不拼接进指令（见 [03](./03-可信安全与隐私.md#2-提示注入防御)）。

## 8. 部署

- 部署地区与备案问题见 [00 第 6 节](./00-总览与决策.md#6-待用户确认的问题)和 [05](./05-落地与里程碑.md)。

## 9. 已确认的架构决定（2026-11-16）

**原则：基础设施尽量简单，核心亮点做深。** 目标是实习岗位，一个人维护得了、每一块都讲得清楚为什么存在。没有 Redis、任务队列和外部观测平台。

### 9.1 以后很难改，已经定下的

| # | 决定 | 内容 | 理由 |
| --- | --- | --- | --- |
| 1 | 代码位置 | 同一仓库，`jobpilot/`（后端，独立 pyproject）+ `web/`（前端）；`app/` 不动 | 避免与旧实验依赖冲突 |
| 2 | 同步 / 异步 | 全部异步：FastAPI async、SQLAlchemy 异步模式 | 主要耗时在等模型；现有模型调用也是异步 |
| 3 | 数据库驱动 | 统一 psycopg 3 | LangGraph 的 Postgres checkpointer 也用它，只有一种驱动 |
| 4 | 长任务执行 | 进程内后台任务；运行状态写数据库，LangGraph 检查点负责断点恢复；前端轮询状态 | 个人使用规模足够。执行入口集中在一个函数，以后换任务队列只改这一处 |
| 5 | 登录 | 自写最小登录：Cookie + 数据库存储的 session（HttpOnly、SameSite=Lax），token 只存哈希；密码 argon2（pwdlib） | 同源网页应用更安全；删掉 session 记录就能让登录立刻失效（两阶段删除账号需要）。不用 JWT：JWT 过期前难以作废 |
| 6 | 主键 | UUID | 防止通过递增 ID 猜测其他用户的数据 |
| 7 | 用户隔离 | 应用层：数据访问函数必须带 user_id，测试遍历全部接口；不做 RLS | 简单好懂；RLS 留作以后的第二道防线 |
| 8 | 删除策略 | **账号两阶段删除**：申请后进入 7 天待删除期，到期由清理任务彻底删除（外键级联）。其他内容（岗位、改写结果等）直接删除，前端二次确认；经历事实靠版本机制保留历史；统计事件匿名保留。最后一道防线是数据库备份 | 账号删除影响最大，需要缓冲期；其他数据只做最简单的保护，不引入全局软删除过滤，避免漏写过滤条件造成泄露。（2026-11-16 修订：原为「全部直接删除」，实施前评审认为账号误删风险过高） |
| 9 | 模型调用 | 自写网关（DeepSeek，OpenAI 兼容接口）：预算、重试、调用记录、不可信内容包装集中在一处；不用 LangChain 模型封装 | 链路透明，面试讲得清楚 |
| 10 | Prompt 管理 | `prompts/` 下一个文件一个 prompt，文件内写版本号；每次运行记录版本 | 评测结果可以复现、可以解释 |

## 10. RAG 设计（V2）

| # | 决定 | 内容 |
| --- | --- | --- |
| R1 | 存储 | 与业务数据同一个 PostgreSQL，pgvector 存向量；HNSW 索引，余弦距离 |
| R2 | 检索方式 | **先只做向量检索**作为基线；「jieba 分词 + Postgres 全文检索 + RRF 融合」作为 E9 对照实验，有数据证明有用才保留 |
| R3 | 知识归属 | 切块表 `owner_id`：为空是公共知识（自己整理的面经、八股），有值是某个用户的私有资料（复盘、笔记）。查询条件为「自己的或公共的」。公共内容入库前人工审核 |
| R4 | 模型记录 | 每个切块记录 Embedding 模型名称与版本，换模型时据此重算 |
| R5 | 切块 | 面经按「一道题 + 答案」切块；长文章按段落递归切分。附公司、岗位方向、技术标签、日期 |
| R6 | 检索流程 | 向量检索取前 k 条；不做重排序 |
| R7 | Agent 使用方式 | 出题规划节点**固定检索一次**；追问时检索作为工具，由面试官 Agent 决定是否调用 |
| R8 | 入库 | 资料表记录来源和版本，切块关联资料；更新时删旧切块重新入库；使用与改写任务相同的后台任务机制 |

带过滤条件的近似检索可能召回不足（索引先取近邻再过滤）。每个用户的私有资料很少，可以不走索引直接计算；需要时使用 pgvector 的迭代索引扫描。这一点在 E9 中顺带验证。

现有 `rag_*.py` 中的切块、上下文组装、引用校验思路沿用；`vector_store.py` 基于 Chroma，需按 pgvector 重写。

## 11. 记忆与上下文管理

### 11.1 四层

| 层次 | 内容 | 存储 | 生命周期 |
| --- | --- | --- | --- |
| 权威数据 | 经历事实库、岗位库 | 业务表 | 永久，用户维护 |
| 长期记忆 | 目标岗位、城市、弱项、偏好 | memory 表 | 跨会话；用户可查看、修改、删除 |
| 短期记忆 | 一场面试的问答；一次改写运行的中间状态 | interview_turn 表；LangGraph 状态与检查点 | 一场面试或一次运行 |
| 上下文 | 每次调用模型时实际放入提示词的内容 | 不单独存储，调用前现场组装 | 一次调用 |

上下文管理 = 每次调用前，决定从前三层里各取什么、取多少。

### 11.2 上下文组装顺序

每一段都有长度上限，超出时按规则截断或压缩：

1. 系统指令（固定）
2. 核心长期记忆（默认放入）
3. 按当前问题选出的普通长期记忆
4. 检索到的知识（V2）
5. 本场已结束考察点的摘要
6. 当前考察点的完整问答
7. 用户本次输入（不可信数据，放在数据区块中）

**程序强制规则：改写简历只读事实库，不读长期记忆。**

### 11.3 各场景的做法

- **模拟面试（V2）：** 当前考察点保留完整问答；已结束的考察点压缩为摘要（问题、回答要点、判断）；整体有 token 上限，超出时先压缩最早的摘要。每轮问答写入 interview_turn，中途离开可以继续。
- **改写流程（V1）：** LangGraph 状态即短期记忆。改写每一条经历时，只放入该条相关的事实和对应的 JD 要求，不放整份事实库和整份 JD。
- **短期转长期：** 面试结束后整理弱项候选，**用户确认后**才写入长期记忆；本场摘要保存，供复盘与检索使用。

### 11.4 深度

- 长期记忆的更新与删除：深做（沿用 [Memory V1.1](../Memory-V1.1轻量分层长期记忆方案.md) 设计，见 E8）。
- 短期记忆与上下文管理：做到能用，加一组对照实验（E11：保留全部历史 vs 摘要 + 当前考察点）。
- 不做：复杂压缩算法、自动判断何时压缩。

可复用的现有代码：`load_recent_messages`（读取最近历史）、`build_memory_context`（组装记忆上下文）、`rag_context.py`（预算内组装检索片段）。
