# 求职主题比较：企业知识 Agent 与年报评测

日期：2026-11-16（Asia/Taipei）。状态：选题建议与证据核查，尚未由用户确认替换原技术调研 V1，未实施新产品。

用户目标是有利于 AI 应用 / Agent 开发求职，同时具备可复现评测、成熟参考实现和可解释的个人贡献。用户提出企业知识可能更常见，且可以用企业年报测评；随后要求独立判断，不能顺着每次疑虑更换推荐。本页使用同一套标准比较主题，记录建议成立的条件。

## 1. 本轮建议及理由

建议主题：**企业知识分析 Agent（Agentic RAG），以公开企业年报作为首个可复现评测场景。**

这是基于岗位关联、已有代码、数据可得性、评分可行性和个人交付范围的综合判断。不是“已统计该主题招聘最多”，也不是“只要做知识库就能求职”。企业知识产品与年报评测分开：首版用年报检验公开文档能力，不能把这份结果扩大为对所有内部知识、权限和长期记忆的验证。

| 标准 | 企业知识分析 | 售后工单处理 | 经营数据分析 / ChatBI | 技术调研与选型 |
| --- | --- | --- | --- | --- |
| 岗位关联 | RAG、文档、工具、上下文、评测和交付有直接关联 | 客服 / 业务系统集成关联清楚 | 有真实 DataAgent 岗位，SQL 与报表交付关联强 | 可展示搜索与长任务，但“后台任务框架选型”业务面偏窄 |
| 可获得输入 | 年报和财务 QA、合成企业资料可公开获取 | τ-Bench 有公开模拟环境；自定义业务还需订单与政策模型 | 自建数据库可控，真实企业指标与业务数据较难取得 | 官方文档公开，但网页与版本持续变化 |
| 可获得评分 | 有答案、证据、数值程序及原始 PDF；需区分不同数据集输入 | 可以核验最终数据库状态和政策约束，评测条件很好 | SQL 结果可验证；业务解释、因果判断较难统一评分 | 事实与引用可评，完整推荐的质量与覆盖复核成本较高 |
| 承接本项目 | 已有 Embedding / Chroma / 引用、工具循环和 Memory；仍需 PDF / 表格 / 研究任务实现 | 可复用 Agent，但要新增工单业务状态、动作契约及工作台 | 可复用 Python / 数据库基础，仍需语义层、查询约束与报表体系 | 最接近此前方案，但产品主题需要更清晰的岗位与评测支撑 |
| 可讲的难点 | 文档解析、混合召回、版本 / 单位、动态补检索、可核验计算、证据与索引更新 | 规则、人工确认、幂等、补偿、工具执行与转人工 | SQL、指标口径、分析任务、受控计算和结果校验 | 证据缺口、版本核对、来源与长任务恢复 |
| 当前取舍 | 优先推进具体设计 | 保留为工具行动类备选；投客服团队时可更贴合 | 保留为数据岗位备选 | 原文档保留为候选设计，不再当作已确定主题 |

表内是对任务和工程范围的判断，不是打分排名。客服并不缺公开评测，知识主题也不天然比客服更先进；对本项目，前者更容易把投入放在业务动作，后者能集中利用已有检索积累并建立公开文档证据链。

## 4. 建议的产品任务与 Agent 价值

产品暂名：企业知识分析助手。第一版处理用户导入的公开企业年报与相关文档，回答事实问题、跨年份比较与受控数值计算，并提供页码 / 原文证据与未知项。先不扩到投资决策、全公司所有数据连接器或自动执行外部业务动作。

代表任务：

1. 找到某公司指定年度的指标或业务说明，展示对应原文及页码。
2. 比较两个年度的同一指标，核对单位、合并 / 母公司等口径，再调用确定性计算工具。
3. 问题有歧义或资料不足时澄清、补查或说明无法确定。
4. 后续任务复用已确认的公司 / 年份 / 输出偏好；修改条件后旧值不能覆盖本次要求。

简单问题走直接检索基线。复杂问题才需要拆解、重复检索、读表、计算和结果核验。Agent 是否有用由同题对照决定，不把每题都变成多 Agent。可考虑工具 search_documents、read_pages、lookup_table、calculate、save_research_note；实际契约和权限待方案确认后设计。

Memory 保存研究偏好、确认条件与经历候选；年报事实仍追溯文档版本，不把旧回答当权威知识。长期记忆、任务 checkpoint 和 RAG 资料仍分工。

## 5. 评测协议的关键约束

- **三种输入条件分报**：给定 gold 证据测生成 / 计算；给定指定文档测文档内查找；全库只给问题测端到端检索。不能把 gold evidence 直接送给模型后称检索成功。
- 全库模式可按用户实际问题识别出的公司 / 年份过滤；不得从答案标签、证据页或未提供的 gold 文档 ID 暗中定位。指定文档模式是否给文件名必须写入协议。
- FinanceBench evidence_page_num 是零起始，界面显示页码转换与 PDF 印刷页码另核对。出处存在与结论受原文支持分别评。
- 数值评测需要金额 / 单位 / 比率 / 百分点 / 正负号 / 舍入规则，计算使用受控工具；不只依赖字符串相同或裁判一句“正确”。
- 公开旧题作为外部基准，另用较新中文年报做公司 / 年份留出测试，减少反复调公开题导致的过拟合。公司 / 文档族整体划分，相关题改写不能跨开发与保留组。
- 中文补充集单报，不能把翻译或改写后的题当原始英文 benchmark；自建题记录标注来源、人工 / 模型评审身份与分歧。
- 除年报 QA 外，必须另测记忆更新 / 删除 / 跨会话、索引增量与旧版本失效、模拟权限过滤、工具错误、任务取消与恢复。只做公开年报不能证明这些能力。
- 比较纯向量 RAG、混合 + rerank、Agentic 检索 / 计算；固定模型、语料、参数和输出上限，记录实际成本、失败、全部尝试及未知用量，不预设提升百分比。
- 文档与数据集许可、再分发条件需按实际资源核对；本轮未下载大语料、安装 PDF 引擎或发起付费评测。

可报告指标包括证据 Recall@k、答案 / 数值正确性、引用支持、拒答、任务成功、工具参数与执行、延迟、Token / 费用及其缺失覆盖。先建设基线与少量开发题，再决定是否值得扩展更多算法或多 Agent。

## 6. 开源参考的采用层次

- **产品与知识管理**：优先比较 Onyx、RAGFlow，重点看导入 / 索引、知识范围、检索与来源；尚未深读全部源码或验证它们当前成绩。
- **长文检索备选**：[PageIndex](https://github.com/VectifyAI/PageIndex/tree/c9f1a879d3b3906ec2617724a905f5cb5e32546e)采用树结构与推理检索，可作为现成对照候选；本轮仅 README 级，不依据厂商自报成绩替换混合检索基线。
- **Harness**：延用[22 项候选池](./2026-11-16-Harness架构候选池与筛选记录.md)，pi、Hermes 等用于学习循环、上下文、Memory 与恢复，实际默认框架尚未定。
- **算法与评分**：保留[功能选型](./2026-11-16-Agent功能与开源选型.md)中的现成 BM25、RRF、重排、结构化校验与语义评分候选，不自创复杂融合 / 记忆打分公式。
- **小型年报项目**：本轮找到 annual-report-rag-agent 等直接相关个人仓库，适合作为数据划分和报告组织线索；项目关注度低、未核验许可证 / 原始结果，不能作为成熟主参考或直接相信其自报通过率。

最终选题建议是企业知识分析 Agent，成立条件是交付可追溯的复杂文档任务、扎实的端到端评测及失败分析。若最终只完成固定 top-k 问答界面，它对广泛 Agent 开发岗位的说服力仍有限。现阶段保持主题比较的状态，不把本页建议写成用户已经确认或产品已经实现。
